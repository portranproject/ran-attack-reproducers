# A-NAS: 완료 컨텍스트 보유와 OCUDU의 두 번째 가드 (2026-10-22)

대상: OCUDU `release_26_10` (`e0db566a`), 셀 n78 TDD 3489.42 MHz, 30 kHz, 51 PRB, 천장 96.
UE: OAI `2026.w38` + rss 재현기. 공격은 **UE 측만** 변조, gNB 소스·설정 무수정.
격리된 자체 테스트베드(AWS p5) 전용.

## 1. 왜 A형이 3% 차이로 막혀 있었나

점유는 `수락률 x 보유시간`이다. 수락률은 gNB의 RA 파이프라인이 **42.5/s**로 묶고
(인스턴스 6→8→12에서 불변), A형의 보유시간은 gNB의 `t300 + rrc_procedure_guard_time_ms`로
고정이다. 이번 세션에서 다시 측정한 값은 **1,999.0 ms**(`ue=2545`)이며, 기존 측정
1,999.4 ± 0.3 ms와 일치한다.

천장 96을 고정하려면 `96 / 2.197 s = 44.6/s`가 필요하다. 42.5/s는 **5% 모자라고**,
그 차이는 gNB가 정하는 양이라 UE 측에서 올릴 수 없다. 이것이 천장 체류율이
35.1%에서 멈춘 이유다.

**우리는 수락률만 공격하고 보유시간은 건드리지 않았다.** `completion_pct` 노브는
있었지만 설명이 "`>0` ends the run at the first one"이었고, 실제로 일회성 점검용이었다.

## 2. Msg5를 보내면 가드가 바뀐다

`RRCSetupComplete`가 도착하면 RRC 설정 가드는 **취소된다**. 완료 컨텍스트는 만료가
없으므로 보유시간이 더 이상 gNB RRC의 소관이 아니다. 문헌에서 이것은 LTEFuzz의
"BTS resource depletion"이고 본 저장소 [rss-landscape.md](../rss-landscape.md) §3.2가
**A-NAS**로 분류해 둔 변종이다(기존 methodology 시나리오 목록에는 없었다).

### 2.1 그냥 완료하면 더 나빠진다 (반증)

설정된 IMSI로 실제 등록 요청을 보내고 코어의 응답만 무시한 경우:

| ue | 완료 | DL NAS | 보유시간 |
|---|---|---|---|
| 2543 | OK | 있음 | **32.0 ms** |
| 2544 | OK | 있음 | **28.4 ms** |
| 2546 | OK | 있음 | 1,473.4 ms |
| 2545 | 미완료(A형) | 없음 | 1,999.0 ms |

AMF는 `amf_ue=4,5,6`으로 **별개 컨텍스트를 만들었다가** DL NAS 송신 후 **0.07 ms 안에**
해제를 시작했다. 인스턴스가 모두 같은 SUPI를 쓰므로 코어가 중복을 정리한 것이다.

→ **식별자가 해소되는 완료는 A형보다 70배 나쁘다.** 완료 자체가 이득이 아니다.

### 2.2 코어가 아무것도 해소·거절할 수 없게 만들면 성립한다

Msg5의 `dedicatedNAS-Message`에서 5GMM 메시지 타입을 미할당 값으로 바꿨다
(평문 5GMM 헤더 `[EPD 0x7E][보안헤더타입][메시지타입]`의 3번째 옥텟).
AMF는 복호에 실패하므로 SUPI를 해소하지 못하고(= 컨텍스트가 하나로 합쳐지지 않는다)
거절할 NAS 절차 자체가 없다.

| ue | 완료 | DL NAS | 보유시간 |
|---|---|---|---|
| 2547 | OK | **없음** | 3,021.2 ms |
| 2548 | OK | **없음** | 3,143.8 ms |
| 2549 | OK | **없음** | 3,143.5 ms |
| 2550 | OK | **없음** | 3,143.1 ms |

`dl_nas = 0`, 설정 성공 **4/4**, 중앙값 **3,143.5 ms**. A형 1,999 ms 대비 **1.57배**.

## 3. 발견: OCUDU의 두 번째 가드 (NGAP 3,000 ms)

해제 원인이 로그에 명시돼 있다.

```
2026-10-22T14:07:59.957501 [NGAP] ue=2547 ran_ue=6:
  UE did not request a PDU session after 3000ms. Releasing UE from DU
```

A형을 묶는 가드(`t300 + guard`, 1,999 ms)와 **별개의 독립 가드**다. A-NAS는 첫 가드를
우회하지만 이 두 번째 가드에 걸린다. 보유시간 3,143 ms = NGAP 가드 3,000 ms + 철거 약 143 ms.

**산술이 바뀐다**: 천장 고정에 필요한 수락률이 `96 / 2.197 = 44.6/s`(부족 5%)에서
`96 / 3.1435 = 30.5/s`로 내려간다. 측정 수락률 42.5/s 대비 **1.39배 여유**다.

## 4. 그런데 수락률이 구속 조건이 아니다

A-NAS는 한 UE 인스턴스가 **동시에 하나의 연결 컨텍스트만** 잡는다. 따라서
A-NAS가 만드는 점유는 수락률이 아니라 **인스턴스 수**로 정해진다.
`MAX_NUM_NR_UE_INST = 32`이므로 A-NAS 단독 상한은 약 31이고, 96에 못 미친다.

그래서 혼합이 필요하다. A-NAS가 H개를 상시 잡으면 A형은 `96 - H`만 채우면 된다.

## 5. 미해결: 공유 ZMQ가 연결 UE 수를 제한한다

| 인스턴스 | A-NAS | 결과 |
|---|---|---|
| 4 | 4 | 정상, 보유시간 측정 성공 |
| 20 | 13 | **붕괴** — `SSS detection on a null signal` 256건, 런 span 약 0.5 s, 스톰 28 시도 |

A-NAS 보유 인스턴스는 **연결 상태로 계속 송신**(PUCCH/SRS/CSI)하므로, 시도 사이에
유휴인 A형 인스턴스보다 공유 무선에 훨씬 무겁다. 20대에서 UE가 하향 동기를 잃는다.

이것은 [normal-ue-denial.md](normal-ue-denial.md)의 프리앰블 합산 붕괴와 같은 계열의
**테스트베드 아티팩트**(공유 ZMQ)이며, 상용 환경의 공격자는 독립 무선을 쓴다.

## 6. 부수 발견 2건

1. **하네스 결함**: `conf/rss.conf`가 `UE_EXTRA=`를 평문 대입하고 `rss-run`보다 먼저
   source되므로, 환경변수로 넘긴 `UE_EXTRA`가 조용히 지워졌다. `UE_EXTRA`에는
   명령행 플래그가 없어 이것이 유일한 경로였다 → 노브가 완전히 닿지 않았다.
   `${UE_EXTRA:-}`로 수정. 이 프로젝트에서 같은 계열의 세 번째 사례다.
2. **CU 로거 정지**: `all_level: debug`에서 20 인스턴스 스톰 중 ocu 프로세스는 살아
   있는데 `/tmp/ocu.log` 기록이 62 MB에서 줄 중간에 끊겼다(디스크는 37 G 여유).
   gNB 설정은 수정 금지이므로 로그 수준을 낮출 수 없고, 관측 복구는 CU 재시작뿐이다.
   측정 창을 잡을 때 CU 로그 연속성을 먼저 확인해야 한다.
3. **CU만 재시작하면 테스트베드가 조용히 망가진다**: 관측을 되살리려고 CU(ocu)만
   재시작하고 DU를 그대로 두었더니, 순수 A형 6대 기준선이 42.5/s·60 s에서
   **1.8 s·51 시도**로 무너졌다(`SSS detection` 87건). `ctl.sh`가 경고하는 대로
   DU는 CU 뒤에 떠야 F1/E2가 정상이다. **CU를 재시작하면 DU도 재시작해야 하고,
   재시작 뒤에는 기준선을 먼저 재측정해야 한다** — 그러지 않으면 붕괴한 무선을
   공격 효과로 오독한다. 이 세션에서 14·20 인스턴스 런을 그렇게 오독할 뻔했다.

## 6a. 인스턴스 상한을 깨는 레버: A-NAS churn

§4의 "인스턴스 1대 = 컨텍스트 1개" 제약은 **깰 수 있다.** OCUDU의 NGAP 가드는
**시간 기반**이므로(§3), 링크를 유지하든 말든 gNB는 완료 컨텍스트를 3초 잡는다.
즉 연결 상태로 앉아 있는 것은 아무 이득이 없고 인스턴스 하나를 소모할 뿐이다.

Msg5 직후 바로 새 RA를 시작하면 점유가 다시 `수락률 x 보유시간`이 된다:
`42.5/s x 3.143 s = 133` (천장 96).

구현이 간단하고 위험도 낮다. `rss_poll()`은 `handle_t300_expiry()`로 끝나는데
**RRC 상태 가드가 없다** — 그래서 `RRC_CONNECTED`에서도 새 RA가 그대로 진행되고,
2026-10-20에 UE를 죽인 UE 주도 해제 경로를 전혀 건드리지 않는다.
노브 `--rss.anas_gap_ms`(기본 80 ms)가 Msg5가 전파에 나갈 시간을 준다
(CU 실측 Msg3→Msg5 21.7 ms, 약 3.7배 여유).

**UE 측 기전은 실증됐다**: 6 인스턴스에서 Msg5가 **5건 → 98건**으로 늘고
`msg4=98`로 모든 Msg4가 Msg5로 전환됐다. 송신율 33.8/s는 §3의 필요값 30.5/s를 넘는다.

### 그러나 gNB 측에서 반증됐다

같은 창(14:51:30–38)의 CU 관측:

| 지표 | 값 |
|---|---|
| `rrcSetupComplete` | 104 (13.0/s) |
| `InitialUEMessage` | **7** (0.9/s) |
| end reasons | `finished successfully: 7`, **`timed out: 32`** |
| 보유시간 중앙값 | **1,999 ms** (3,143 아님) |
| 컨텍스트 생성 | 44건 (**5.5/s**) |
| 최대 점유 / `rrcReject` | 27 / **0** |

Msg5 104건 중 **7건만** 완료 컨텍스트가 됐고 32건은 **1,999 ms에 타임아웃**했다.
Msg5를 큐에 넣고 80 ms 뒤 새 RA를 시작하면 UE가 그 C-RNTI를 버리므로 CU가 절차를
끝내지 못하고, 컨텍스트는 A형 미완료 경로(1,999 ms)로 되돌아간다. 게다가 Msg5
왕복이 A형 1회보다 비싸서 **생성률이 42.5/s → 5.5/s로 무너진다.**

**결론: churn은 3,143 ms 가드를 얻지 못한다.** 그 가드는 NGAP 컨텍스트가 실제로
생길 때만(= UE가 그만큼 연결을 유지할 때만) 적용된다. 따라서 §4의
"인스턴스 1대 = 컨텍스트 1개" 제약은 **유효하며, 깨지지 않았다.**

## 6b. 측정을 막는 테스트베드 문제 2건 (미해결)

1. **UE 코어 덤프**: 무거운 런에서 약 2초 뒤 UE가 죽는다
   (`Error, channel timeout` → `Resynchronizing RX` → `dumped core`).
   세션 첫 런은 4 인스턴스로 45초를 완주했으므로(2,584 시도) 스택이 건강할 때는
   가능하다. 반복된 무거운 런 뒤에 나타난다. 원인 미규명 — rss 패치는 anas_ues=0
   에서 전부 no-op이므로 패치 탓이라고 단정할 근거는 없다.
2. **CU 로거 정지 재발**: §6의 2번이 반복된다. 로그가 끊기면 점유 실측 창을
   잡을 수 없고(`rss-report`가 "log timestamps do not cover the window"로 거부),
   복구는 CU+DU 순차 재시작뿐이다.

→ 그래서 §6a의 기전은 실증됐지만 **천장 96 상시 점유와 정상 UE 차단은
   아직 실측되지 않았다.**

## 7. 구현 (UE 측만)

- 노브 `--rss.anas_ues N` — 인스턴스 `[probe_ues, +N)`이 Msg5를 보내고 코어에 응답하지 않는다
- `rrc_UE.c` Msg5 결정에 `!nr_rss_is_anas()` 추가 → A-NAS는 정상 경로로 간다
- NAS 블라인딩 2곳: 버퍼 경로(`NAS_INITIAL_UL_TRANSFER_REQ`)와 **즉석 생성 경로**
  (`generateRegistrationRequest` 직후). 후자를 빼먹으면 A-NAS가 설정된 IMSI로
  실제 등록을 해 §2.1의 붕괴가 난다
- DL NAS 전달을 `!nr_rss_is_anas()`로 차단 → 인증 요청에 답하지 않는다
- 망이 해제하면 재부착(`nr_rrc_going_to_IDLE`에서 재무장). 망 주도 해제이므로
  2026-10-20에 UE를 죽인 UE 주도 해제 경로(SAT-1019T220108Z)와 다르다

## 8. 판정

**조건 미달.** 정상 UE 프로브는 측정된 모든 조건에서 **첫 시도에 접속**했고
(최종 런 194 ms, 상실 0), `rrcReject`는 어떤 창에서도 관측되지 않았다.

성립한 것과 안 한 것을 분리하면:

| 항목 | 상태 |
|---|---|
| A형이 3%로 막힌 이유가 **보유시간**이라는 진단 | 확인 (§1) |
| Msg5 송신이 RRC 설정 가드를 취소한다 | 확인 (§2) |
| 해소 가능한 식별자로 완료하면 **더 나빠진다** | 확인, 70배 (§2.1) |
| NAS 블라인딩으로 코어가 응답하지 않게 만들기 | 확인, `dl_nas=0`, 완료 4/4 (§2.2) |
| **OCUDU NGAP 3,000 ms PDU 세션 가드** 발견 | 확인 (§3) |
| 보유시간 1,999 → 3,143 ms (1.57배) | 확인 (§2.2) |
| 필요 수락률 44.6/s → 30.5/s | 산술 (§3) |
| 인스턴스 상한을 churn으로 깨기 | **반증** (§6a) |
| 천장 96 상시 점유 | 미실증 |
| 정상 UE 연결·통신 차단 | **미실증** |

### 왜 이 테스트베드에서는 막히는가

점유는 `min(인스턴스 수, 수락률 x 보유시간)`이다. A-NAS는 두 번째 항을 133까지
올리지만(96 초과) **첫 번째 항에 걸린다**: 완료 컨텍스트 하나당 UE 인스턴스 하나가
연결을 유지해야 하고, `MAX_NUM_NR_UE_INST = 32`이며, 실제로는 공유 ZMQ가
건강한 인스턴스를 그보다 훨씬 적게 제한한다(§5, §6b).

A형은 반대다. 인스턴스 6대로 42.5/s를 내지만 보유시간이 1,999 ms로 고정이라
점유가 93.4에서 멈춘다.

**두 상한이 서로 다른 축에 있어서, 둘을 합치려면 인스턴스를 많이 띄워야 하고
그건 공유 무선이 막는다.** 이것이 남은 단일 구속 조건이고, 공유 ZMQ는
테스트베드 아티팩트다 — 상용 환경의 공격자는 독립 무선을 쓴다.

OTA에서는 A-NAS가 A형보다 유리하다. 필요 수락률이 30.5/s로 내려갔으므로
A형이 요구하던 44.6/s보다 여유가 크고, 인스턴스가 독립 무선을 쓰면 §4의
상한도 사라진다.

## 9. 정정 (같은 날 후반): 기준 수락률 42.5/s 가 과소값이었다

§1~§3의 산술은 수락률 42.5/s를 전제로 한다. **건강한 스택에서는 더 높다.**
프로브를 포함한 8 인스턴스가 **54.4/s**(2,231 시도 / 41.0 s)를 냈고,
`rrcReject` 39.2/s, `not able to serve` 13.1/s가 나왔다.

42.5/s와 §5의 "공유 ZMQ 인스턴스 상한" 판단은 상당 부분 **CU만 재시작해
F1이 깨진 스택에서 측정한 값**이었다(§6b 3번). 11 인스턴스는 건강한 스택에서도
`sss` 손실이 크지만(240건), 8 인스턴스는 41초를 완주했다.

따라서 §8의 "두 상한이 서로 다른 축에 있다"는 결론은 유지되지만,
**A형 단독 수락률이 천장 고정 요구치 44.6/s를 이미 넘는다**는 점이 달라진다.
천장 체류는 여전히 0%인데, 이는 수락률 부족이 아니라 gNB의 이력현상
(천장에서 일괄거절 → 점유 급락, 72~95 진동) 때문이다.

**그리고 목표 달성 경로는 A-NAS가 아니었다.** 같은 건강한 스택에서
재수립 위조 축출이 정상 UE를 실제로 끊어냈다 —
