# OCUDU: 인증 없는 재수립 요청으로 제3자 UE 를 해제할 수 있다

발견 2026-10-22. 소스 판독 + **실행 실증**. 설치본 `release_26_10` (`e0db566a`).

## 요약

OCUDU CU-CP 는 DU 가 새 UE 를 수용하지 못해 DU-to-CU RRC 컨테이너를 비워 보낸 상태에서
`RRCReestablishmentRequest` 를 받으면, 요청에 적힌 **(PCI, C-RNTI) 만으로** 기존 UE 를 찾아
**그 UE 의 컨텍스트 해제를 요청**한다. 이 분기에서 `shortMAC-I` 는 검증되지 않는다.

A형 시그널링 스톰이 바로 그 전제조건(DU 포화 → 빈 컨테이너)을 만든다. 따라서 공격자는
스톰으로 문을 열고, 위조 재수립 요청으로 **제3자를 밖으로 내보낼 수 있다.**

## 코드 (설치본 직접 판독)

`lib/rrc/ue/rrc_ue_message_handlers.cpp:118-140`

```cpp
void rrc_ue_impl::handle_rrc_reest_request(const asn1::rrc_nr::rrc_reest_request_s& msg)
{
  metrics_notifier.on_attempted_rrc_connection_reestablishment();

  // If the DU to CU container is missing, assume the DU can't serve the UE, so the
  // CU-CP should reject the UE, see TS 38.473 section 8.4.1.2.
  if (du_to_cu_container.empty()) {
    rrc_ue_reestablishment_context_response old_ue_reest_context =
        cu_cp_notifier.on_rrc_reestablishment_request(
            msg.rrc_reest_request.ue_id.pci,
            to_rnti(msg.rrc_reest_request.ue_id.c_rnti));

    // Release the old UE.
    logger.log_debug("Requesting UE context release for old_ue={}", old_ue_reest_context.ue_index);
    cu_cp_notifier.on_rrc_reestablishment_failure(
        {.ue_index = old_ue_reest_context.ue_index,
         .cause = ngap_cause_radio_network_t::unspecified});

    // Reject and release the new UE.
    logger.log_warning("Sending rrcReject. Cause: DU is not able to serve the UE");
    on_ue_release_required(ngap_cause_radio_network_t::unspecified);
    return;
  }
  // ... 정상 경로: rrc_reestablishment_procedure
}
```

`verify_short_mac_i()` 는 존재하지만 **정상 경로에만** 있다
(`lib/rrc/ue/procedures/rrc_reestablishment_procedure.cpp:262`). 위 분기는 그 앞에서 `return` 한다.

## 실증 (2026-10-22)

UE 측만 변조(OAI `nr-uesoftmodem`). 스톰 인스턴스가 천장을 채우고, 축출 인스턴스가
`do_RRCReestablishmentRequest()` 로 C-RNTI 를 열거하며 `shortMAC-I = 0` 으로 보낸다.
AS 보안 컨텍스트는 없다(상류 `nr_rrc_ue_prepare_RRCReestablishmentRequest()` 의
`AssertFatal(rrc->as_security_activated, ...)` 경로를 우회).

CU 로그 실측:

```
Rx SRB0 CCCH UL rrcReestablishmentRequest   = 125   (위조 요청이 CU 에 도달)
Requesting UE context release for old_ue    =  21   (CU 가 제3자 해제를 요청)
```

**125건 중 21건이 살아 있는 컨텍스트를 찾아 해제를 유발했다.**
적중률 17% 는 열거 범위(0x4601~0x4700, 256개) 대비 당시 생존 컨텍스트 수와 일치한다.

## 조준에 피해자 정보가 필요 없다

DU 는 C-RNTI 를 좁은 범위에서 순차 할당한다(로그: `0x4601`, `0x4602`, `0x4604`, `0x4606`…).
256개 열거를 측정된 ~60 시도/s 로 돌리면 4초에 한 바퀴다. 피해자의 C-RNTI 를 알 필요가 없다.

추가로 이 셀은 PRACH 기회가 하나뿐이라 **모든 UE 가 RA-RNTI 를 공유**하므로, 공격자는
피해자에게 가는 RAR 을 이미 복호하고 그 TC-RNTI 를 수확할 수도 있다.

## 영향 등급

- **인증 우회**: `shortMAC-I` 는 재수립 때 UE 를 검증하는 값인데(TS 38.331 §6.3.2)
  이 경로에서 검사되지 않는다
- **제3자 서비스 거부**: 연결된 UE 를 임의로 해제할 수 있다
- **원격·무인증 트리거**: 공격자는 가입자 자격이나 AS 보안 컨텍스트가 필요 없다.
  필요한 것은 (a) 셀에 RA 를 성공시키는 능력과 (b) DU 포화 상태다.
  (b) 는 공격자가 스스로 만든다
- 다만 **전제조건이 DU 포화**이므로 평시에는 정상 경로(`shortMAC-I` 검증)를 탄다

## 규격 근거

TS 38.473 §8.4.1.2 는 컨테이너가 없으면 CU 가 **새 UE 를 거절**하라고 한다:

> "If neither the DU to CU RRC Container IE nor the Sidelink Configuration Container IE
> ... is included in the INITIAL UL RRC MESSAGE TRANSFER, the gNB-CU should reject the UE
> under the assumption that the gNB-DU is not able to serve such UE."

규격은 **새 UE 거절**만 요구한다. OCUDU 는 거기에 더해 **기존 UE 를 찾아 해제**하는데,
그 조회가 인증되지 않는다. 즉 규격이 요구하지 않은 동작에서 인증이 빠졌다.

## 측정의 구조적 한계: 포화된 셀과 건강한 피해자를 동시에 둘 수 없다

축출 분기는 `du_to_cu_container.empty()` 를 요구하고, 그건 **천장 96 포화**를 뜻한다.
포화는 스톰이 60~70/s 로 돌아야 생긴다. 그런데 프로브(정상 UE)를 같은 프로세스에 두면
공유 ZMQ 가 무너져 스톰이 10~20/s 로 떨어진다. 실측:

| 런 | 프로브 | 스톰 시도/s | 컨텍스트 생성(창) | 재수립 CU 도달 | **제3자 해제** |
|---|---|---|---|---|---|
| (앞선 런, 프로브 영향 적음) | 있음 | ~15 | — | **125** | **21** |
| g_on | 있음 | ~9 | 46 | 5 | **0** |
| g_off2 | 있음 | ~14 | 35 | 0 | 0 |
| g_on2 | 있음 | ~10 | 45 | 4 | **0** |

컨텍스트 생성이 35~46 으로 천장 96 에 못 미치는 창에서는 DU 가 UE 를 정상 수용하므로
컨테이너가 비지 않고, 위조 요청은 **정상 경로**로 가서 `shortMAC-I` 검증에 걸린다.
그래서 제3자 해제가 0 이다. 기전의 문제가 아니라 전제조건 미달이다.

즉 다음이 동시에 필요한데 이 테스트베드에서는 양립하지 않는다.

- 축출 분기 발동 → 스톰이 **강해야** 함
- 피해자 생존 측정 → 스톰이 **약해야** 함 (프로세스 내 프로브의 공유 라디오 한계)

| 항목 | 상태 |

## 이 한계를 넘는 방법 (전부 이 세션 범위 밖)

1. **피해자를 별도 프로세스·별도 무선으로** — DU 에 두 번째 RF 포트가 필요하므로
   기지국 설정 변경이다. 실 SDR OTA 면 자연히 해결된다
2. **정상 UE 가 여럿인 배치** — 그러면 생존 컨텍스트 대부분이 피해자이므로
   맹목 열거의 희석이 사라진다. 코어 가입자가 필요하고, 그건 사용자가 폐기한 접근이다
   (다만 폐기 이유는 "천장 낮추기" 였고, 여기서는 **피해자 모집단 확보** 라는 다른 목적이다 —
   그래도 정상 UE 가 통신 중이라는 전제가 성립하므로 같은 자기모순을 안는다)
3. **gNB 측 관측으로 대체** — 해제된 UE 가 완료 컨텍스트였는지
   (`"RRC Setup Procedure" finished successfully` 와 해제 ue_index 대조)를 보면
   프로브 없이도 "정상 접속을 끝낸 UE 가 해제됐는가" 를 판정할 수 있다.
   이것이 다음 세션의 가장 값싼 다음 수다

## full-strength 창 실측 (프로브 없음, 2026-10-22 13:13:07–13:14:32)

```
Rx SRB0 CCCH UL rrcReestablishmentRequest   =   10
Requesting UE context release for old_ue    =    3   (old_ue=690, 697, 703)
RRC Setup Procedure" started                = 1417
RRC Setup Procedure" finished successfully  =    0
Sending rrcReject                           =   48
점유: 평균 74.0, 피크 96, 천장 체류 3.6%
```

**`finished successfully = 0` 이 핵심 식별자다.** 재현기는 설계상 `RRCSetupComplete` 를
보내지 않으므로 완료 컨텍스트는 **정상 UE 만** 만들 수 있다. 0 이라는 것은 이 창에
정상 UE 가 없었다는 뜻이고, 따라서 해제된 3개는 **공격자 자신의 미완료 컨텍스트**다.

식별자가 작동하므로 **측정 방법은 옳다** — 프로브(공유 라디오 아티팩트) 없이
"정상 접속을 완료한 UE 가 축출됐는가" 를 판정할 수 있다. 필요한 것은
정상 UE 존재 + 천장 포화의 동시 성립이고, 그것이 이 테스트베드에서 양립하지 않는다.

누적 확인: 위조 요청 134건 수신, 제3자 컨텍스트 해제 24건 (21 + 3).

## 다음 세션의 결정적 실험 (설계 완료, 실행만 남음)

프로브 없이 gNB 측 관측만으로 판정한다. 필요한 조건은 하나다 —
**정상 UE 1대가 셀에 붙어 있고 동시에 천장이 포화**되어야 한다.

- 실 SDR OTA 면 정상 UE 가 독립 무선을 쓰므로 자연히 성립한다
- ZMQ 에서는 `ctl.sh ue` 로 정상 UE 를 먼저 붙인 뒤 스톰을 **별도 UE 프로세스**로
  올리는 방법을 시험해 볼 수 있으나, 두 프로세스가 같은 ZMQ 포트쌍을 다투므로
  성립 여부가 미확인이다
- 판정식: 창 안에서 `"RRC Setup Procedure" finished successfully` 의 `ue=` 와
  `Requesting UE context release for old_ue=` 의 인덱스가 일치하면
  **정상 UE 가 인증 없이 축출된 것이 실증된다**

## 조준 해결: 남의 RAR 에서 C-RNTI 수확 (2026-10-22)

심사와 나 자신이 "공격자가 피해 UE 의 C-RNTI 를 알 수단이 없다" 로 닫았던 문제는
**성급했다. 공격자는 이미 그 정보를 수신하고 있었고 버리고 있었다.**

이 셀은 PRACH 기회가 하나뿐이라 RA-RNTI 가 전 UE 공통이고(실측), 따라서 공격자는
**피해자에게 가는 RAR 을 복호한다.** 상류 코드는 RAPID 가 자기 것이 아니면 그 subPDU 를
버린다. 그 RAR 에는 gNB 가 방금 발급한 TC-RNTI 가 실려 있고, 그것이 그 UE 의 C-RNTI 가 된다.

구현: `nr_ue_procedures.c` RAR 파싱 루프의 RAPID 불일치 분기에서
`other->TCRNTI_2 + (other->TCRNTI_1 << 8)` 를 수확 링(256칸)에 넣고, 축출기가 그 값을
우선 사용한다. 자기 TC-RNTI 는 제외한다.

**실측: 축출 요청 21건 중 20건이 조준(`targeted: true`)**, 수확된 실제 C-RNTI
(`0x4601`, `0x4605`, `0x463c`, `0x464b`). 맹목 열거(1/256)가 직접 조준으로 바뀌었다.

주의: 자기 C-RNTI 제외 집합은 프로세스 전역인데 프로브도 같은 프로세스에 있어
처음에는 **피해자를 자기 편으로 분류**해 수확 링이 비었다(조준 0). 프로브를 등록에서
제외해 고쳤다. 실제 공격에서는 공격자와 피해자가 별개 장비이므로 전역 집합이 옳다.

## 남은 단 하나의 고리: 동시 성립

n_on 창 (13:28:33–13:29:22) 실측:

```
조준 C-RNTI (수확)                          = 0x4601, 0x4605, 0x463c, 0x464b
Rx SRB0 CCCH UL rrcReestablishmentRequest   = 10
Requesting UE context release for old_ue    =  0
RRC Setup Procedure" finished successfully  =  1   ← 정상 UE 존재
RRC Setup Procedure" started                = 55
```

정상 UE 가 있었고, 조준이 실제 수확값이었고, 위조 요청이 CU 에 도달했는데 **해제는 0건**이다.
컨텍스트 55개로 천장 96 에 못 미쳤으므로 `du_to_cu_container.empty()` 가 성립하지 않아
요청이 **정상 경로**로 가서 `shortMAC-I` 검증에 걸렸다.

### 고리별 입증 상태

| 고리 | 상태 | 증거 |
|---|---|---|
| 1. 천장 포화 → 빈 컨테이너 | **실측** | 거절 6,564줄 전부 해당 cause |
| 2. 피해자 C-RNTI 확보 | **실측** | 조준 20/21, 수확값 4종 |
| 3. 인증 없는 위조 요청 전송 | **실측** | CCCH 수신 누적 134건 |
| 4. CU 가 제3자 컨텍스트 해제 | **실측** | `release for old_ue` 누적 24건 (ue=690/697/703 등) |
| **1~4 동시 성립** | **미실증** | 프로브가 있으면 스톰이 천장에 못 닿는다 |

**모든 고리가 개별로 입증됐고 동시 성립만 남았다.** 이것이 "취약점 실증" 과
"정상 UE 차단 실증" 의 차이이며, 섞어 쓰지 않는다.

# 정정 (2026-10-22 후반): 동시 성립이 ZMQ 에서 실증됐다

위의 "동시 성립 미실증" 과 "OTA 가 유일한 길" 은 **틀렸다.** 두 전제가 모두 틀렸다.

### 틀린 전제 1 — "축출 분기는 천장 포화를 요구한다"

요구하지 않는다. 분기 조건은 `du_to_cu_container.empty()`, 즉 **DU 가 그 UE 를
받지 못하는 것**이고, 그건 천장 100% 체류 없이도 상시 일어난다. 실측:

```
not able to serve   496   13.1/s
```

천장 체류는 0% 였는데도(점유가 72~95 에서 진동) 축출 기회가 **초당 13회** 있었다.
프로브 재접속이 200~600 ms 이므로 필요량은 약 5/s 다. 처음부터 충분했다.

### 틀린 전제 2 — "프로세스 내 프로브가 스톰을 10~20/s 로 떨어뜨린다"

그 10~20/s 는 **망가진 스택에서 측정한 값**이었다(CU 만 재시작해 F1 이 깨진 상태).
건강한 스택에서 프로브를 포함한 8 인스턴스는 **54.4/s** 를 냈다 — 기존 기준값
42.5/s 보다 높고, 천장 고정에 필요한 44.6/s 보다도 높다.

### 실측 1: `f_ev` (수확 조준, 8 인스턴스, 41.0 s)

스톰 2,231 시도(54.4/s), 축출 시도 1,798건(조준 1,369 / 스윕 429),
CU 도달 재수립 요청 1,772건, `rrcReject` 39.2/s, 점유 72~95 가 창의 92%.

프로브(정상 UE) 접속 3회 중 **2회가 축출됐다**. UE 측 보고 `conn=3 LOST=2`,
접속 지연 353 → 2,751 → **5,298 ms** (15배 악화).

| 프로브 접속 | 접속 완료 | 사용자평면 | 위조 요청에 의한 해제 |
|---|---|---|---|
| `ue=128` | 15:02:44.529 | **PDU 세션 성립** 15:02:45.817 | `rrcRelease` 15:02:46.718 (+2.19 s) |
| `ue=155` | 15:02:48.769 | **없음** | `rrcRelease` **+27 µs** |
| `ue=300` | 15:02:49.516 | PDU 세션 성립 | 생존 |

`ue=155` 가 가장 깨끗하다 — 정상 접속을 끝낸 **27 µs 뒤** 해제됐고 사용자평면에
도달하지 못했다. 그 창에서 `Requesting UE context release for old_ue=155` 가 7건이다.

### 실측 2: `g_ev` (스윕 범위 정정)

`f_ev` 에서 `ue=300` 이 살아남은 이유는 스윕 범위를 `lo=1, hi=65535` 로 둔 내 실수다.
실제 C-RNTI 는 `0x4600` 대인데 스윕이 `0x0001`, `0x0002` … 를 때리고 있었다.
`lo=0x4600, hi=0x4700` 으로 고치자 약 6초 창에서 **축출 61건(약 10/s)**,
프로브 접속 **1회 중 1회 축출**:

```
15:06:50.349594  ue=2280 c-rnti=0x4606: Rx SRB1 DCCH UL rrcSetupComplete
15:06:50.349680  ue=2280: "RRC Setup Procedure" finished successfully
   (Initial Context Setup 없음, PDU Session Resource Setup 없음)
15:06:52.317205  ue=2283 c-rnti=0x4609: old_ue=2280 ... Requesting UE context release
15:06:52.317452  ue=2280: Tx SRB1 DCCH DL rrcRelease (8 B)        ← 247 µs 뒤
```

정상 UE 가 접속을 끝내고, 사용자평면에 못 가고, **인증 없는 위조 요청 247 µs 뒤**
끊겼다. 요청의 `shortMAC-I` 는 0 이다.

### 해제 메시지가 두 형태다 (둘 다 `shortMAC-I = 0` 으로 도달)

1. `old_ue=N was not fully attached yet. Requesting UE context release`
2. `Requesting UE context release for old_ue=N`

본문 §가 다룬 것은 2번이지만 1번도 제3자를 해제하며 위조 요청으로 도달한다.

### 중요 정정: 1번 분기는 용량 압력을 전혀 요구하지 않는다

본문과 위 "실측 1~2" 는 축출이 `du_to_cu_container.empty()`(= DU 거절 압력)를
요구한다고 적었다. **1번 분기에는 해당하지 않는다.** 실측(`q_t2`, 58.1 s 창):

```
not able to serve   0
rrcReject           0
위조 재수립 요청     1,732
```

압력이 **전혀 없는데도** 정상 UE 가 끊겼다. 그리고 그 UE 는 PDU 세션까지 받은
**완전히 서비스 중인 UE** 였는데 로그는 "was not fully attached yet" 이라고 적는다:

```
15:41:15.230641  ue=1623: "RRC Setup Procedure" finished successfully
15:41:15.457243  ue=1623: "Initial Context Setup Procedure" finished successfully
15:41:15.708461  ue=1623: "PDU Session Resource Setup Procedure" finished successfully
15:41:17.301741  ue=1639 c-rnti=0x4621: old_ue=1623 was not fully attached yet.
                 Requesting UE context release          ← 위조, shortMAC-I = 0
15:41:17.303327  ue=1623: Tx SRB1 DCCH DL rrcRelease    ← 1.6 ms 뒤
```

즉 OCUDU 의 "fully attached" 판정이 실제 서비스 상태와 일치하지 않으며,
**임의의 (PCI, C-RNTI) 위조만으로 서비스 중인 제3자를 끊을 수 있다.**
이는 본문이 기술한 것보다 **심각도가 높다** — 셀을 포화시킬 필요가 없으므로
공격 비용이 훨씬 낮고, 인스턴스 수·무선 안정성 제약도 사라진다.

### 실측 3: 가용성 대조 (조준 집중 후)

조준을 라운드로빈 → **최신 수확 우선**으로 바꾸자 조준율이 76% → **99.1%** (743/750)
가 됐다. 같은 날 측정한 정상 UE 가용성 대조:

| 조건 | 창 | 프로브 연결 시간 | PDU 세션 획득 |
|---|---|---|---|
| 대조: 셀 압력 없음 (5 인스턴스) | 96.5 s | **98.7%** | **2 / 2** |
| 처리: 축출 + 압력 (`m_foc2`, `rrcReject` 393) | 30.3 s | **75.5%** | **4 / 6** |

처리군에서 2개 컨텍스트는 사용자평면 도달 전에 끊겼다(`ue=721` +62 ms,
`ue=1223` +127 ms). 그러나 `ue=1085` 는 **12.8 s 동안 PDU 세션을 유지**했다.

**조준이 살아 있는 피해자에게서 벗어난다**는 뜻이다. 축출기 6대가 모두 수확하므로
더 새로운 non-own C-RNTI 가 계속 "최신" 자리를 밀어낸다. 고착 조준(1,000 ms 유지)을
구현했으나 그 뒤 두 런이 3.5 s·5.0 s 에서 동기 손실로 무너져 **효과 미측정**이다.

### 지배적 제약: 두 요구가 서로 충돌한다 (양쪽 모두 실측)

| 인스턴스 | 안정성 | 셀 압력 | 축출 | 정상 UE |
|---|---|---|---|---|
| 5 | **96 s 완주** | 없음 (`rrcReject` 0) | 위조 요청 116건이 **정상 경로**로 가 `shortMAC-I` 검증에 걸림 | 98.7% 가용, PDU 2/2 |
| 8 | 3~41 s (간헐) | `not able to serve` 13.1/s | 작동 (f_ev 2/3, g_ev 1/1, m_foc2 2/6 가 사용자평면 차단) | 75.5% 가용 |

축출 분기는 DU 거절 압력을 요구하고, 그 압력은 약 50/s 스톰 = 약 8 인스턴스를
요구하는데, 8 인스턴스는 **공유 ZMQ RX 를 고갈시켜 UE 가 하향 동기를 잃는다**
(`SSS detection on a null signal`, `Error, channel timeout`).
`f_ev` 가 41초를 버틴 것은 운이었다.

> 참고: `timeout: the monitored command dumped core` 는 `timeout` 래퍼의 메시지다.
> UE 는 3초에 죽는 것이 아니라 **하향 동기를 잃고 복구하지 못한 채** 외부 타임아웃
> (65 s)에 종료된다. 이것을 UE 크래시로 오독했었다.

### 실측 4: 고착 조준 + UE 코어 고정 — 가용성 92.8% → 5.3%

두 가지를 바꿨다.

1. **고착 조준**: 최신 수확 우선에 1,000 ms 유지를 더했다. 축출기 6대가 모두
   수확하므로 최신 우선만으로는 살아 있는 피해자에게서 조준이 계속 벗어났다
   (`m_foc2` 에서 `ue=1085` 가 12.8 s 동안 PDU 세션 유지).
2. **UE 코어 고정**: `UE_TASKSET=2-7`. **gNB(odu)는 고정하지 않았다** — gNB 의
   CPU 를 제한하면 테스트베드가 상용보다 약해지므로 금지 사항이다. 공격자 UE 만
   고정하면 odu 는 8코어 전부를 그대로 쓸 수 있다.

동일 구성(8 인스턴스, 동일 고정)에서 축출만 끄고 켠 대조:

| 런 | 축출 | 창 | 위조 요청 | 프로브 연결 시간 | PDU 세션 |
|---|---|---|---|---|---|
| `q_ctl` | **OFF** | 28.1 s | 0 | **92.8%** | 2 / 3 |
| `p_stk2` | ON | 22.7 s | 998 | **19.8%** | 1 / 3 |
| `q_t2` | ON | 58.1 s | 1,732 | **5.3%** | 1 / 2 |

`q_t2` 에서 정상 UE 는 **58초 중 94.7% 를 연결 없이** 보냈고 접속 자체가 2회만
성공했다(대조는 28초에 3회). 사용자평면에 도달한 1회도 위조 요청 **1.6 ms 뒤**
끊겼다(위 §"중요 정정" 의 `ue=1623` 로그).

### 실측 5: 전체 표본과 용량-반응 (약 12회 시도)

고착 유지시간을 노브로 빼고(`--rss.evict_sticky_ms`, 기본 150 ms) 표본을 늘렸다.
150 ms 로 줄인 근거는 정상 UE 가 사용자평면에 도달하는 시간(ICS +41~891 ms,
PDU +306~1,421 ms)보다 짧아야 조준이 먼저 도착한다는 것이다.

긴 창(50초 이상)을 얻은 전체 표본:

| 런 | 위조 요청 | 요청/s | 프로브 연결 시간 | PDU 세션 |
|---|---|---|---|---|
| `q_ctl` (대조, 축출 OFF) | 0 | — | **92.8%** | 2 / 3 |
| `t_c` | 72 | 1.3 | 97.5% | 1 / 2 |
| `s_t2` | 180 | 3.2 | 96.1% | 2 / 3 |
| `t_d` | 388 | 21.7 | 79.0% | 2 / 3 |
| `p_stk2` | 998 | 44 | 19.8% | 1 / 3 |
| `q_t2` | 1,732 | 30 | **5.3%** | 1 / 2 |
| `u_ctl` (대조2, 축출 OFF) | 0 | — | **99.0%** | 2 / 2 |
| `u_t1` (라운드로빈 조준) | 208 | 3.6 | 96.7% | 2 / 2 |

**용량-반응은 있으나 단조롭지 않고 분산이 크다** (44/s → 19.8% 인데 30/s → 5.3%).
요청률이 낮은 런(1~3/s)에서는 축출이 **대조군보다도 가용성이 높게** 나와
사실상 무효다.

약 12회 시도 중 긴 창은 6회, 그중 강한 차단(20% 미만)은 **2회**였다. 나머지는
3~5초에서 하향 동기를 잃었다(`SSS detection on a null signal`). UE 코어 고정이
성공률을 올렸지만 없애지는 못했다.

### 실측 6: 조준 정확도가 6% 였다 — 그리고 조준 실험이 평가 불가다

위조 요청이 **살아 있는 피해자를 실제로 지목했는지** 직접 셌다(`q_t2`,
`attempt_start` 의 `target_crnti` vs CU 로그의 프로브 C-RNTI):

```
forged requests with a target: 1740   distinct targets: 18
   0x4676   1619          ← 예산의 93%, 프로브가 아니다
   0x4611    105  <== PROBE  (6.0%)
```

고착 조준이 **이미 존재하지 않는 C-RNTI `0x4676`** 에 예산의 93% 를 쏟았다.
own 필터가 동작하면 링에 non-own 항목이 둘뿐이고, 고착은 그중 "최신" 하나에
예산 전부를 주차한다. 그게 죽은 값이면 전부 낭비다.

**그런데 프로브를 지목한 105건만으로 가용성 5.3% 가 나왔다**(= 1.8/s 로 94.7% 무연결).
즉 조준이 전부다. 15/s 를 제대로 지목하면 완전 차단이 기대된다.

그래서 라운드로빈으로 되돌렸으나(`evict_sticky_ms=0` 기본),
**이어진 런들이 모두 요청률 3.6/s 로 굶어서 조준 변경의 효과를 측정할 수 없었다**
(`u_t1` 96.7%). 고착 대 라운드로빈은 **미결**이다.

### 실측 7: 연령 창으로 조준 6.0% → 46.9%, 그래도 차단은 안 된다

수확 링에 슬롯별 타임스탬프를 붙이고 **연령 창**으로 걸렀다
(`--rss.evict_min_age_ms` 150, `--rss.evict_max_age_ms` 4000).
너무 어린 값은 아직 own 등록 안 된 우리 자신의 TC-RNTI(초당 약 42개 유입),
너무 늙은 값은 `0x4676` 처럼 이미 사라진 값이다. 살아 있는 피해자는 재접속마다
다시 수확되므로 창 안에 머문다 — 재수확 시 타임스탬프를 갱신하게 했다.

`v_t3` (44.0 s, 위조 312건, 7.1/s):

```
requests aimed AT the probe: 181 (46.9%)      ← 6.0% 에서 개선
   0x4607    181  <== PROBE  (ue=1596, +1798 ms 에 이미 해제된 컨텍스트)
   0x4719      0              ← ue=1859, PDU 세션 유지하며 38 s 생존
   0x47ab      0
```

| 런 | 조준 정확도 | 프로브 연결 시간 |
|---|---|---|
| `v_ctl` (대조) | — | 97.7% |
| `v_t3` (연령 창) | **46.9%** | 93.1% |

**조준은 올랐는데 차단은 안 됐다.** 181건 전부가 프로브의 **첫 번째** C-RNTI
(이미 죽은 것)에 갔고, 이후 두 C-RNTI 는 **아예 수확되지 않았다**.

### 병목이 한 단계 내려갔다: 차단 ← 조준 ← 수확 커버리지

- 조준: **해결** (연령 창, 6.0% → 46.9%)
- **수확 커버리지: 프로브 접속 3회 중 1회만 포착** ← 새 병목

그리고 C-RNTI 공간이 런마다 **표류한다**: `q_t2` 에서 `0x4611`/`0x464a` 였는데
`v_t3` 에서는 `0x4719`/`0x47ab` 다. 정적 스윕 범위(`0x4600`~`0x4640`)는 죽은 범위가
됐다. **고정 스윕은 원리적으로 틀렸다** — 할당기를 따라가야 한다.

### 부작용 1건: 연령 창이 과하게 걸러낼 수 있다

`v_t2` (56.1 s)에서는 적격 항목이 없어 축출이 **6건**으로 떨어졌다
(정상 시도는 1,041건). `min_age=150 ms` 가 런에 따라 너무 공격적이다.
적격 항목이 0이면 스윕으로 폴백하는 경로가 필요하다.

### 실측 8: 적응형 스윕 — 자기 축출 회귀와 그 수정, 결과는 77.5%

관측한 최대 C-RNTI 를 따라가는 스윕을 넣었다
(`--rss.evict_adaptive`, `--rss.evict_window`).

**먼저 자기 축출 회귀가 났다.** 창을 좁게(6~32) 두면 그 범위가 **가장 최근 할당된
C-RNTI** 로 채워지는데 그건 거의 다 공격자 자신의 것이다. `rrc_UE.c` 의 own 가드
루프는 `span` 번만 돌고 **own 값을 그대로 들고 나오므로**, 자기 컨텍스트를 끊는다.
4런 중 3런이 **0.6초**에 죽었다.

수정: 범위가 전부 own 이면 위조를 포기하고 평범한 설정 요청을 보낸다.
창 기본값도 32 → 64 로 올렸다(좁은 창은 non-own 후보를 고갈시킨다).

수정 후 `x_t1` (60.9 s, 위조 406건, 조준 73.6%):

| | 프로브 연결 시간 | PDU 세션 |
|---|---|---|
| `x_t1` (적응형 스윕 w=64) | **77.5%** | 2 / 3 |

**`q_t2` 의 5.3% 를 재현하지 못했다.** `t_d` 의 79.0% 와 같은 수준이다.

### 현재 판정과 멈춘 지점

긴 창 8건 전체에서 강한 차단은 **`q_t2` 1건(5.3%)** 뿐이고, 나머지는 77~99% 로
대조군(92.8~99.0%)과 크게 다르지 않다. **지속적 차단은 재현되지 않았다.**

체인 이해는 진전됐다:

```
차단  ←  조준  ←  수확 커버리지
      6% → 74%     접속 3회 중 1회 (미해결)
```

조준은 연령 창으로 고쳤지만(6.0% → 46.9% → 73.6%) 차단으로 이어지지 않았다.
`q_t2` 가 5.3% 를 낸 이유는 조준율이 높아서가 아니라(6.0%) **프로브를 지목한
105건이 그 프로브의 수명 내내 집중됐기** 때문으로 보인다. 즉 중요한 것은
조준율이 아니라 **살아 있는 피해자에게 연속적으로 도달하는 것**이고,
그건 수확이 매 접속을 포착해야 성립한다.

### 내가 만든 회귀 4건 (전부 수정)

| 회귀 | 증상 | 수정 |
|---|---|---|
| 스윕 범위 `lo=1` | 죽은 범위(`0x0001`~)를 때림 | 실범위 → 적응형 |
| 고착 조준 | 죽은 C-RNTI 에 예산 93% | 연령 창 + 라운드로빈 |
| 분석기 연결시간 | 미해제 컨텍스트를 0초로 계산 | 창 끝까지 과금 |
| 적응형 좁은 창 | **자기 컨텍스트 축출** → 0.6초 사망 | own 전체면 위조 포기 |

### 실측 9 (결정적): 축출은 **접속 직후 과도 구간**에만 통한다

CU 로그 전체에서 모든 `old_ue=N ... context release` 에 대해 N 의
`"RRC Setup Procedure" started` 시각을 찾아 **축출 당시 컨텍스트 나이**를 쟀다.

```
축출-접속 매칭 건수: 120
메시지 형태: {'not fully attached': 93, 'release for old_ue': 27}
축출 시점 나이(ms):  min 657  p50 2473  p90 6165  p99 7077  max 7157

   0-500 ms          0  (0.0%)
   500-1000 ms       7  (5.8%)
   1000-2000 ms     15  (12.5%)
   2000-3000 ms     74  (61.7%)
   3000-5000 ms      9  (7.5%)
   5000-10000 ms    15  (12.5%)
   >10 s             0  (0.0%)
```

**120건 중 7.2초보다 오래된 컨텍스트를 끊은 사례가 단 하나도 없다.** 62% 가 2~3초에
몰린다. 즉 **접속 직후 약 7초 안에만 통하고, 그 창을 넘긴 UE 는 면역이 된다.**

이것이 세션의 모든 측정을 설명한다:

- `z_a3`: 조준 98.6%, 위조 **1,455건** 인데 프로브 상실 **0회**, 가용성 99.7%.
  프로브가 0.2초에 붙어 창을 넘겼으므로 이후 1,455건이 전부 무효였다
- 모든 런의 공통 패턴 — 처음 몇 초간 교란, 그 뒤 프로브가 정착해 끝까지 유지
- `q_t2` 의 5.3% 는 조준이 좋아서가 아니라, 그 창에서 프로브가 **계속 재접속하며
  매번 과도 구간에 머물렀기** 때문이다

### 그래서 목표 조건의 성립 요건이 바뀐다

지속적 차단은 "요청률" 이나 "평균 조준율" 의 문제가 아니다.
**매 접속마다 약 2초 안에 반드시 명중시켜야 하는 경쟁(race)** 이다.
한 번 놓치면 그 UE 는 런이 끝날 때까지 안전하다 — 중간값이 없는 all-or-nothing 이다.

현재 재현기는 그 경쟁을 **일부만** 이긴다. 그래서 가용성이 5.3%(전승에 가까운 창)
부터 99.7%(첫 접속에서 놓친 창)까지 흔들린다.

### 측정 방식 정정 (중요)

CU 로거가 부하에서 약 10초에 멈춘다. 61초 런을 9.8초 창으로만 보고
`y_s1` 을 "가용성 44.2%" 로 읽었는데, UE 측 프로브 이벤트로 **전체 창**을 재면
**99.0%** 였다. 교란은 처음 5초에 다 일어나고 그 뒤 56초를 붙어 있었다.

→ **1차 지표는 UE 측 `ue_avail.py`(전체 창)** 로 쓴다. CU 로그는 인과 확인용이다.
   이 결함 때문에 한동안 차단 효과를 과대평가했다.

### 다음 레버 (요건 재정의 반영)

1. **접속 순간 명중** — 과도 구간이 약 2초이므로, 프로브의 RA 를 포착한 즉시
   그 C-RNTI 에 집중 발사해야 한다. 수확이 매 접속을 놓치지 않는 것이 전부다
2. **전승 여부로 평가** — 평균 가용성보다 "접속 n 회 중 몇 회를 2초 안에 잡았나"
   가 올바른 중간 지표다. 현재 측정은 이 값을 직접 재지 않는다
3. **실 SDR OTA** — 수확 누락과 런 간 변동이 모두 공유 가상 무선의 아티팩트다

### 실측 10: 스윕 전용 반증 — 그리고 완결된 인과 설명

수확 경로를 끄고(`evict_min_age_ms` 를 크게) **스윕 전용**으로 돌렸다. 지금까지
모든 런은 수확이 스윕을 선점해(`targeted=True` 가 73~98%) 스윕이 제대로 시험된
적이 없었다.

| 런 | 축출 시도 | 요청/s | 프로브 연결 시간 |
|---|---|---|---|
| `s_ctl` (대조) | 0 | — | **99.6%** |
| `sw16` | 78 | 1.4 | 99.6% |
| `sw32` | **2,232** | **36.6** | 99.3% |
| `sw64` | 160 | 6.5 | 98.8% |

**36.6/s 로 2,232건을 쏟아도 대조군과 구별되지 않는다.** 스윕 전용은 무효다.

### 완결된 인과 설명

1. 축출은 **접속 후 약 2~7초 창**에서만 통한다 (120/120, 최대 7.16 s — 실측 9)
2. 정상 UE 는 **174~326 ms** 에 접속을 완료하고 그 뒤 면역이 된다
3. 따라서 지속적 차단은 **피해자의 첫 접속부터 매 접속마다 2초 내 명중**을
   요구하는 경쟁이며, 한 번 놓치면 그 UE 는 런이 끝날 때까지 안전하다
4. 스윕은 그 경쟁을 이길 수 없다 — 대역을 훑는 동안 피해자는 이미 면역이다
   (`sw32`: 2,232건 → 99.3%)
5. 수확 기반 조준은 **때때로** 이긴다 — 피해자의 RA 를 포착한 순간 그 C-RNTI 를
   때리므로 창 안에 들어간다. `q_t2` 의 5.3% 가 그 경우다
6. 그런데 공유 ZMQ 에서 수확은 **프로브 접속 3회 중 1회만** 포착한다(실측 7).
   그래서 전승이 안 되고 가용성이 5.3%~99.7% 로 흔들린다

→ **남은 구속 조건은 수확 커버리지 하나이며, 그것은 공유 가상 무선의 아티팩트다.**
   독립 무선(실 SDR OTA)이면 각 인스턴스가 피해자의 RAR 을 놓치지 않는다.
   용량 고갈 경로는 별개로 이미 막혀 있다(gNB 수락 제어가 93.4/96 에서 묶는다).

### 실측 11: 실험 설계 편향 제거 — 그래도 안 된다

지금까지 프로브는 공격자와 **같은 순간** 출발했다. 프로브는 174~326 ms 에 접속을
끝내는데 그때 축출기들은 아직 RA 를 올리는 중이라, 프로브가 첫 경쟁을 **구조적으로**
이기고 그 뒤 면역이 됐다. 즉 모든 런이 피해자에게 유리하게 편향돼 있었다.

노브 `--rss.probe_delay_ms` 를 추가해 프로브가 **스톰이 10초간 전속으로 돈 뒤**
도착하게 했다(목표 조건이 말하는 상황: 이미 공격받는 셀에 정상 UE 가 도착).
프로브의 접속을 실패시키는 것이 아니라 **언제 요청하는지만** 바꾼다.

| 런 | 축출 | 거절 | 프로브 도착 | 결과 | 연결 시간 |
|---|---|---|---|---|---|
| `p_t1` | 92 | 0 | 10.11 s | **1회 시도에 접속**, 56초 유지 | 84.7% |
| `p_t2` | 644 | 241 | 10.13 s | 2회 시도(+130 ms), 이후 유지 | 84.4% |

**편향을 없애도 결과가 바뀌지 않는다.** 644건의 축출과 241건의 거절이 흐르는 셀에
도착해도 프로브는 130 ms 안에 수립하고 그 뒤 버틴다.

→ 프로브가 이기는 이유는 "먼저 출발해서" 가 아니다. **공격이 새 접속을 면역 창
   안에 잡아낼 수 없기** 때문이다. 잡으려면 그 창 안에 피해자의 C-RNTI 를 알아야
   하고, 유일한 경로인 RAR 수확이 공유 ZMQ 에서 3회 중 1회만 성공한다.

(`p_ctl` 은 10.1초에 무선 동기를 잃어 유효한 대조가 아니다. 다만 처리군 84% 가
기존 대조군 92.8~99.6% 와 큰 차이가 없어 결론은 바뀌지 않는다.)

### 실측 12: `q_t2` 재현 실패 — 5.3% 는 이상치로 취급해야 한다

세션 내내 `q_t2`(가용성 5.3%)를 "작동하는 설정" 으로 다뤘지만, **한 번도 그 설정을
그대로 재현해 본 적이 없었다.** 계속 거기서 멀어지는 방향으로 "개선" 했다.

`q_t2` 이후 추가한 것은 모두 노브이므로 되돌릴 수 있다:
`evict_sticky_ms=150`, `evict_min_age_ms=0`, `evict_max_age_ms=999999`,
`evict_adaptive=0`, 정적 범위, 프로브 지연 없음.

3회 재현 시도 결과:

| 런 | span | RA | 축출 | 가용성 |
|---|---|---|---|---|
| `r1` | **3.0 s** | 72.2/s | 189 | 94.5% |
| `r2` | **4.4 s** | 14.9/s | 48 | 95.4% |
| `r3` | **2.4 s** | 17.4/s | 34 | 89.4% |

**3/3 모두 2~4초에서 무선 동기를 잃어 평가 불가.** 재현 여부를 확인하지 못했다.

이것과 "긴 창 8건 중 1건" 이라는 사실을 합치면, 가장 방어 가능한 해석은
**5.3% 를 작동 설정의 증거가 아니라 이상치로 보는 것**이다. 앞선 절들에서
`q_t2` 를 근거로 세운 설명(연속 도달 가설 등)도 그만큼 약하게 읽어야 한다.

### 상관 분석: 요청률·점유율은 차단을 예측하지 못한다

| 런 | RA/s | PRACH 점유 | 수확조준 건수 | 가용성 |
|---|---|---|---|---|
| `q_t2` | 28.7 | 29% | 1,723 | **5.3%** |
| `p_stk2` | 16.0 | 16% | 960 | 19.8% |
| `z_a3` | 36.1 | 36% | 1,455 | **99.7%** |
| `d1` | 29.5 | 29% | 201 | 87.7% |
| `sw32` | 41.8 | 42% | 0 | 99.3% |
| `t_d` | 8.5 | 8% | 391 | 79.0% |
| `v_t3` | 9.9 | 10% | 270 | 93.1% |
| `x_t1` | 8.8 | 9% | 295 | 77.5% |

`z_a3` 는 `q_t2` 보다 RA 율·점유율·조준 건수가 **모두 높은데** 가용성이
99.7% 대 5.3% 로 정반대다. → **요청률·점유율·조준 건수 어느 것도 차단을
예측하지 못한다.** `ra_depth` 로 점유를 올리려는 시도는 RA 율을 29.5 → 1.2/s 로
**붕괴**시켜 반증됐다(실측 12 직전 `d2`/`d4`).

### 최종 판정 (조사 종료)

**목표 조건 — 정상 UE 가 연결·통신을 수행할 수 없는 상태 — 는 이 테스트베드에서
달성되지 않았고, 두 경로 모두 한계가 정량화됐다.**

| 경로 | 한계 | 근거 |
|---|---|---|
| 용량 고갈 | 점유가 93.4/96 에 묶인다. gNB 수락 제어가 설계대로 동작 | 수락률 상한 x 보유시간, 이력현상 |
| 재수립 축출 | 접속 후 약 2~7초 창에서만 통하고, 그 창 안에 C-RNTI 를 알아야 한다. 수확 성공률 1/3 | 120/120 축출이 7.16 s 이내, `sw32` 2,232건 → 99.3%, `p_t1/t2` 84% |

시도하고 측정한 수단: A-NAS 보유시간, A-NAS churn, 완료 컨텍스트, 프리앰블 합산,
RAR 가로채기, 조준 5종(라운드로빈·최신우선·고착·연령창·적응형스윕·스윕전용),
UE 코어 고정, 프로브 도착 시점. **모두 반증 또는 불충분.**

남은 단일 레버는 **수확 커버리지**이고 그것은 공유 가상 무선의 아티팩트다
→ 실 SDR OTA.

### 이 결과 자체의 가치

**지속적 차단은 이 결함으로 달성할 수 없다는 것이 구조적으로 밝혀졌다**(면역 창 존재).
동시에 **접속 과도 구간에서는 인증 없이 제3자를 끊을 수 있다**는 것이
120건으로 정량화됐다. 제보 관점에서는 후자가 핵심이고, 영향 범위를
"수립 중 UE 의 서비스 거부" 로 정확히 한정할 수 있다.

→ **(구) 방법론적 블로커 정정**: "안정된 고요청률이 선행 조건" 이라고 적었는데,
   `v_t3` 은 7.1/s 로도 조준이 46.9% 까지 올랐다. 요청률보다 **커버리지**가
   구속 조건이다.

### 분석기 결함 1건 (수정)

`probe_avail.py` 가 "창 끝까지 해제되지 않은" 컨텍스트의 연결 시간을 **0 으로**
계산했다. PDU 세션을 약 56초 유지한 컨텍스트가 0초로 읽혀 가용성 3.5% 라는
거짓 수치가 나왔고, 창 끝까지로 과금하도록 고치자 **96.1%** 였다.
위 표의 `q_ctl`·`p_stk2`·`q_t2` 는 모든 프로브 컨텍스트에 명시적 해제가 있어
이 결함에 영향받지 않는다(확인함).

### 판정

**정상 UE 가 인증 없이, 용량 압력 없이 축출되는 것은 실증됐다** — 인과 사슬 포함,
서비스 중(PDU 세션 보유) UE 포함.

**목표 조건(정상 UE 가 연결·통신을 수행할 수 없는 상태)은 미충족이다.**

최선의 창(`q_t2`)에서 정상 UE 가용성이 92.8% → **5.3%** 로 떨어지고 58초 중
94.7% 가 무연결이었지만, 이것은 **긴 창 6건 중 1건**이다. 전형적인 런은 79~97.5%
가용성으로 대조군과 구별되지 않거나 더 높다(§실측 5). 지속적 차단이 아니다.

구속 조건은 **위조 요청률**이고, 그것은 공유 ZMQ 무선의 상태에 따라 런마다
1.3/s ~ 44/s 로 흔들린다. 즉 공격 설계가 아니라 **테스트베드 무선 안정성**이
결과를 지배한다.

   약 6회 중 2회다. 남은 탐색: `RSS_LOCKSTEP_WINDOW`·`RSS_ZMQ_TX_WAIT_US`,
   UE 코어 범위 조정, DU 호스트 상향(c6i.4xlarge). **gNB 프로세스 고정은 금지**
   — 상용보다 약한 표적을 만든다
2. **남은 약 2초 서비스 창 제거** — `q_t2` 의 `ue=1623` 은 PDU 세션을 2.07초
   유지했다. 고착 유지시간(현재 1,000 ms)을 정상 UE 접속 지연(200~660 ms)보다
   짧게 하거나, 수확이 접속 즉시 C-RNTI 를 잡도록 보강
3. **표본 확보** — 위 두 항목이 되면 긴 창 10회 이상으로 평균·분산을 낸다
4. **실 SDR OTA** — 1번이 테스트베드 아티팩트이므로 근본 해법

### 패치 상태

조준 변경분(최신 우선 + 고착)과 코어 고정은 **박스에만 있고 저장소 패치에 미반영**
이다. 박스는 stop 이므로 소스는 보존돼 있고, `rrc_timers_and_constants.c` 의
`nr_rss_pick_victim_crnti()` 와 그 위 sticky 정적 변수에서 뽑으면 된다.
`rss-storm/patch/rss-ue-anas.patch` 에는 A-NAS 만 들어 있다.

**다만 "연속 차단" 은 아니다.** `f_ev` 에서 `ue=300` 과 `ue=128` 은 짧게라도 PDU
세션을 받았다. 남은 간격은 **커버리지와 지속**이며 원리가 아니다:

- UE 가 무거운 런에서 코어 덤프해 창이 6~41 s 로 제한된다(`anas_ues=0` 에서도
  발생 → A-NAS 와 무관, 부하 관련, 원인 미규명)
- 축출이 모든 접속을 잡지는 못한다. 스윕 범위 정정으로 크게 개선됐으나
  (1/1) 표본이 6초 창 1건이다

→ 다음 단계는 OTA 가 아니라 **UE 코어 덤프 해결 + 스윕 정정판의 장시간 반복**이다.
