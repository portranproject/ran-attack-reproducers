## 16. "아예 불가능한가" — 공중 시간 기준으로는 거의 선형, 실시간이면 2~3대로 가능 ✅

### 16.1 핵심 측정: UE 수에 따른 두 시계 ✅

| UE 수 | 사이클(공중) | **공중 기준 시도율** | air/wall | 벽시계 시도율 | CU 동시 점유 |
|---|---|---|---|---|---|
| 1 | 40 ms | **26.0/s** | 0.290 | 4.16/s | 19 |
| 2 | 20 ms | **47.2/s** | 0.250 | 7.55/s | 31 |
| 4 | — | (측정 실패, §16.3) | — | (이전 빌드 7.6/s 상당) | 39 |

**공중 시간 기준으로는 1→2대에서 26.0 → 47.2/s로 거의 선형으로 증가한다.**
즉 공유 라디오는 공중 시간 예산을 "나눠 쓰는" 것이 아니라 실제로 **합산 처리량을 늘린다**.
벽시계 점유가 19 → 31로만 늘어난 이유는 `air/wall`이 0.290 → 0.250으로 함께 떨어졌기 때문이다.

### 16.2 실시간 환경 환산 — 2~3대면 포화 ✅

| 조건 | 시도율 | 보유 2 s 기준 동시 점유 | 상한 96 |
|---|---|---|---|
| 단일 UE, 실시간 | 25/s | **50** (관측 지연 보정 시 50~64) | 미달 |
| **2대, 실시간** | 47/s | **94** | **거의 도달** |
| **3대, 실시간** | 약 70/s | **140** | **초과 → 거절 발생** |

**결론: "아예 불가능"은 아니다.** 도구는 공중 시간 기준으로 이미 충분한 속도를 내며,
**실시간으로 도는 환경에서는 2~3대로 기본 설정(96, 2 s)을 포화시킬 수 있다**(산술 추정 🔍).
이 테스트베드에서 안 되는 단일 원인은 `air/wall ≈ 0.25~0.29`다.

단, 실시간 환경에서 2대가 선형 2배를 내려면 **각 UE가 독립 라디오**를 가져야 한다(OTA 또는
충분히 빠른 머신). 공유 라디오에서 선형성이 유지되는지는 `air/wall` 하락분까지 함께 봐야 한다.

### 16.3 구현 상태 — 공유 읽기를 링 버퍼로 재작성 🔶

2·4·6대가 지점만 다르게 깨진 공통 원인을 찾았다: 공유 **읽기**가 라운드 방식이라
**UE가 요청한 샘플 수와 다른 개수를 돌려줬다.** `syncInFrame()`은 자기만의 단위를 요청하므로
`Assertion (unitTransfer == res) failed! nr-ue.c:714`로 죽었다.

→ **링 버퍼 + UE별 커서**로 재작성했다: 한 UE가 장치에서 채우고, 각 UE는 자기 커서에서
**요청한 만큼 정확히** 가져간다. 타임스탬프도 커서 기준으로 환산한다.

| 상태 | 결과 |
|---|---|
| 빌드 | ✅ 경고 0, 29/29 링크 |
| 1 UE | ✅ 정상, 25.1/s 유지(패리티), 라벨 `ue=0`·`max_seq=217` |
| 2·4 UE | ❌ `cc == tx_stream.channels_.size()` (ZMQ 채널 타임아웃 후속 증상) |

**단 이번 세션의 스택은 불건강했다** — `ctl.sh up`이 `odu 기동 실패 — CU가 먼저 start 돼 있는지 확인`을
냈다. 따라서 2·4대 실패가 링 재작성 탓인지 스택 탓인지 **아직 분리되지 않았다** 🔍.
이전 빌드(라운드 방식)에서는 2대 497회·4대 878회가 성공한 기록이 있다(§13.3).

**다음 한 수**: CU부터 깨끗하게 올린 뒤 2대를 재시험한다. 그래도 같은 실패면 ZMQ 채널
타임아웃(`zmq_poll` 10 ms, "Error, channel timeout")을 늘려 본다 — UE 측 장치 코드라 수정 가능하다.

### 16.4 라벨 per-UE 수정 완료 ✅

`rss_seq`가 모듈 전역이어서 다중 UE의 시도 스트림이 섞였다(2대 런의 "Msg3→Msg4 = 10 ms"가 그 증상).
이제 **레코드마다 `ue` 필드**가 있고 **seq는 UE별**이다. 분석기 운영자가 UE 단위로 조인할 수 있다.

```json
{"type":"event","run_id":"RG1","ue":0,"seq":17,"t_ns":...,"air_ms":...,"event":"attempt_start", ...}
```

## 17. "기본 설정·현 환경에서 마비가 불가능한가" — 불가능하지 않다 (자원 측정)

### 17.1 결정적 측정: DU 박스는 CPU가 남는다

run `CPU1`(단일 UE, 공격 중 정상 상태 샘플 4회, 3초 간격):

```
odu              cpu = 171 ~ 173 %   (1.7 코어)   threads=12
nr-uesoftmodem   cpu =  27 ~  34 %   (0.3 코어)   threads=29
loadavg 2.42  /  nproc 8            → 약 6 코어 유휴
air_per_wall = 0.323                   공중 24.8/s, 벽시계 4.04/s
```

**8코어 중 2.1코어만 쓰는데 공중 시계가 0.32배다.** 두 프로세스 모두 계산이 아니라 **대기** 중이다.
슬롯마다 ZMQ REQ/REP 왕복이 필요하고(μ=1이면 초당 2000 슬롯), 그 왕복 지연이 공중 시계를 늦춘다.
→ **지연 바운드이고 CPU 바운드가 아니다.** §13.4에서 "공유 라디오가 UE 수와 무관하게 고정 예산을
가진다"고 쓴 설명은 CPU 고갈을 암시했는데, 그 부분은 틀렸다.

### 17.2 그래서 산술로는 4대면 닿는다

실측 관계: 동시 점유 ≈ 4.3 × 벽시계 시도율 (19 ÷ 4.4/s). 96에 필요한 벽시계 시도율은 약 **22/s**.

`벽시계 시도율 = 공중 시도율 × air_per_wall`

| UE 수 | 공중 시도율(실측/추정) | air_per_wall(실측) | 벽시계 | 예상 동시 점유 |
|---|---|---|---|---|
| 1 | 24.8/s | 0.323 | 4.0/s | 19 (실측 19) |
| 2 | 47.2/s | 0.250 | 7.6/s | 31 (실측 31) |
| **4** | **약 100/s** (선형 가정) | 0.25 가정 | **25/s** | **약 96~100** |

**즉 공중 시도율이 4대까지 선형으로 늘기만 하면 기본 설정(96, 2000 ms)에서 포화에 닿는다.**
1→2대는 실제로 선형이었다(24.8 → 47.2/s).

### 17.3 막고 있는 것은 공유 구현이다

4대 실측 동시 점유는 39(벽시계 약 9/s)로 위 예측의 1/3이다. 즉 **4대에서는 공중 시도율이
선형을 유지하지 못한다.** 자원(코어)은 남아 있으므로 원인은 구현 쪽이다. 현재 공유 계층은:

- 읽기와 쓰기를 **단일 뮤텍스 하나로** 직렬화한다.
- UE마다 슬롯당 `memcpy`를 한 번씩 한다(링 → UE 버퍼).
- 쓰기 합산과 장치 전송을 **락을 쥔 상태로** 수행한다.

UE가 늘면 슬롯당 직렬 구간이 길어지고, 이것이 ZMQ 왕복 지연에 더해져 공중 시계를 더 늦춘다.
6대에서 `Error, channel timeout` → 채널 0 → 어서션으로 죽는 것도 같은 설명과 맞는다
(DU의 `zmq_poll` 인내 10 ms를 넘김).

### 17.4 결론

- **불가능하지 않다.** 자원은 남아 있고(6코어 유휴), 산술은 4대면 96에 닿는다고 말한다.
- **단 지금 구현으로는 안 된다.** 4대에서 선형성이 깨지고, 6대는 기동하지 못한다.
- 다음 레버는 환경이 아니라 **공유 계층의 직렬 구간 축소**다:
  읽기/쓰기 락 분리, 링에서 UE 버퍼로의 복사 제거(커서 포인터 전달), 합산·전송을 락 밖으로,
  필요하면 ZMQ 폴 타임아웃 상향.
- 이것은 산술과 자원 가용성에 근거한 **예측이며 실증은 아니다**. 4대에서 공중 100/s가 실제로
  나오는지 확인해야 결론이 된다.

## 18. 10 ms 프레임을 못 지킨 근본 원인 — UE ZMQ 송신 폴 타임아웃 (해결)

§14~§17은 "공중 시간이 벽시계의 0.25~0.49배"를 환경 성능 문제로 다뤘다. 원인은 성능이 아니라
UE ZMQ 장치의 대기 구조였다. 고친 뒤 **기본 gNB 설정·현 환경에서 단일 UE로 동시 점유 94/96**에
도달했다.

### 18.1 원인

`radio/zmq/zmq_radio.cpp`의 `tx_poll_thread()`는 소켓 이벤트로만 깨어난다.

```c
if (reply_requested) {
  if (chan->pop_message(&msg)) { send; reply_requested = false; }
  // 샘플이 아직 없으면 아래로 떨어진다
}
int rc = zmq_poll(&item, 1, 10); // 10ms timeout
```

DU가 REQ를 보낸 뒤 UE의 TX 큐가 아직 비어 있으면, DU는 REP만 기다리므로 새 소켓 이벤트가 오지
않는다. `zmq_poll`은 자기 타임아웃 10 ms를 꽉 채우고 리턴하고, 그 다음에야 큐를 다시 본다.
UE와 DU는 같은 호스트에서 `tcp://127.0.0.1`로 통신하므로(런 로그 `ue.log` CMDLINE) 전송 지연은
수십 µs다. 즉 10 ms는 전송 지연이 아니라 **타임아웃 상수**이고, 로컬 TX 큐의 1 ms 미만 지각이
무선 프레임 하나를 통째로 잡아먹는다. 수신 경로(`zmq_rx_channel::receive`)는 같은 상황을
`usleep(100)`으로 처리한다 — 송신만 10 ms였다.

### 18.2 계측으로 확인

`RSS_ZMQ_TX_WAIT_US` 노브를 추가했다. 0이면 원래 동작, 기본 100은 100 µs 간격 재확인.
굶은 REQ 수와 그 대기 시간을 함께 적산한다(두 값 모두 노브와 무관하게 계측).

원래 동작(`RSS_ZMQ_TX_WAIT_US=0`, run `ZWA0-043049Z`):

```
[ZMQ] TX antenna 0: 4250 REQs starved / 36203 served, 42555 ms waiting for the local TX queue
```

- 굶음 비율 4250/40453 = **10.5%**
- 굶음당 42555/4250 = **10.01 ms** → `zmq_poll` 타임아웃 10 ms와 일치. 기계적 증거.
- 42.5 s는 UE 프로세스 수명(약 50 s)의 **85%**다.

### 18.3 변경 전/후 비교 (단일 UE, gNB 설정 기본값 2000 ms/96, 환경 무변경)

판정은 CU 로그(`/tmp/ocu.log`)에서 `"RRC Setup Procedure" started`와 그 종료를 ue id로 묶어
동시 점유를 센 것이다 → `reproducers/rrc-signaling-storm/analysis/cu_occupancy.py`.

| | `=0` (원래) | `=100` (수정) |
|---|---|---|
| run | `ZWA0-043049Z` | `ZWA100-043229Z` |
| air_per_wall | 0.46 ~ 0.54 | **2.39 ~ 2.42** |
| 굶음당 대기 | 10.01 ms | 0.185 ms |
| REQ 처리량 | 36,203 | 219,597 |
| 벽시계 시도율(평균) | 6.7/s | **20.0/s** |
| **동시 점유 피크** | **20 / 96** | **94 / 96** |
| 보유 시간(중앙, 벽시계) | 1999 ms | 1644 ms |
| 종료 사유 | timed out 202 | cancelled 590, timed out 11 |

air_per_wall 2.4는 공중 시간이 실시간보다 **빠르게** 흐른다는 뜻이다. ZMQ에는 페이싱이 없으므로

### 18.4 종료 경로가 CU 타임아웃이 아니었다

수정 후에는 601건 중 **590건이 `"RRC Setup Procedure" cancelled`**로 끝난다. CU의 2000 ms
타임아웃이 아니라 **DU가 `UeContextReleaseRequest`를 먼저 보낸다.**

```
04:33:07.900952 ue=790 "RRC Setup Procedure" started
04:33:09.493009 ue=790 Received "UeContextReleaseRequest"   (+1.592 s)
04:33:09.493011 ue=790 "RRC Setup Procedure" cancelled

보유 시간이 2000 ms가 아니라 중앙값 1644 ms인 이유다. 점유 모델에 쓸 값은 2000이 아니라 **1644 ms**.

### 18.5 깨져 있던 측정 도구 2개

- `collect.sh`의 `SINCE`는 `$0 >= "04:32:29"` 로 **행 전체**를 비교했다. 행은
  `2026-10-20T04:...`로 시작하므로 모든 행이 통과한다 → 런 구간 필터가 전혀 작동하지 않았고,
  "timed out 413"처럼 전체 로그 합계를 런 값으로 읽었다. 시간 필드만 비교해야 한다.
- `deploy.sh`는 `nr-uesoftmodem` 타깃만 빌드했다. `zmq_radio.cpp`는 런타임 로드되는 별도
  공유 라이브러리(`liboai_zmqdevif.so`, `--device.name oai_zmqdevif`)로 빌드되므로,
  `radio/zmq/` 수정은 소스 트리에만 반영되고 **실행에는 닿지 않았다**. 지금은 세 타깃을 빌드하고
  `.so`에서 노브 문자열을 확인한다.

### 18.6 재현 확인 (60초 런)

run `ZWB60-044132Z`, 같은 설정으로 길이만 2배:

```

peak occupancy 94    at 04:41:55
hold time wall median 1627 ms  p90 1777 ms
end reasons    {'cancelled': 1151, 'timed out': 19}

94/1.627 ≈ 58/s까지 올라간다. 96을 넘기려면 지속 59/s 이상이 필요하다 — 지금은 상한을

### 18.7 함정: run_id 두 번째 글자가 'O'면 UE가 기동하지 못한다

`CONF-043717Z`, `CONF2-043950Z` 두 런이 `error: file --rss.log_file does not exist` 후
SIGSEGV로 죽었다. 원인은 OAI 업스트림 버그다
(`common/config/config_load_configmodule.c:232`, `2026.w38`):

```c
for (i = 0; i < argc; i++) {
  if (strlen(argv[i]) < 2) continue;
  if (argv[i][1] == 'O' && i < (argc - 1)) {   /* '-' 를 확인하지 않는다 */
    cfgparam = argv[i+1];
    OoptIdx = i;
  }
```

두 번째 글자가 `O`인 **모든** 인자가 `-O`로 오인되고 바로 뒤 인자가 설정 파일 경로가 된다.
`CONF…` → `C` `O` → 뒤따르는 `--rss.log_file`을 파일로 열려다 실패한다. 루프에 `break`가 없어
마지막 매치가 이기는 점도 작용했다(run_id가 인자 목록 끝 근처).

`ZWA100-`, `ZWB60-`은 두 번째 글자가 `W`라 영향이 없었다. `run_attack.sh`가 이제 거부한다.
처음에는 "간헐 실패"로 보였는데 `-d 60`과 run_id를 동시에 바꿨기 때문이다. 한 번에 한 변수.

### 18.8 남은 것

- 점유 94/96는 피크이고 30초·60초 런에서 동일하게 94다. `rrcReject`는 각 3건(상한을 스쳤다).
  지속 포화에는 59/s 이상이 필요하다 → UE 2대 또는 시도당 비용 절감.
- air_per_wall 2.4는 실시간보다 빠르다. 공격 강도는 올라가지만 **더 이상 실시간 재현도 아니다.**
  탐지 성능을 실시간 기준으로 보고하려면 페이싱을 넣어 1.0으로 맞춘 런이 따로 필요하다.
- DU 측 ZMQ에도 같은 10 ms 패턴이 있을 수 있다(동일 코드 계열). gNB 무수정 원칙이라 못 고친다.
  air/wall 2.4가 나왔으므로 지배적 병목은 아니었다.
- §16~§17의 "다중 UE로 96에 닿는다" 계획은 더 이상 필요 조건이 아니다. 단일 UE로 닿았다.

## 19. 단일 UE를 더 끌어올리려는 시도 — 6가지 전부 실패, 천장 측정됨

§18 수정 후 다시 잰 기준선(단일 UE, gNB 기본 설정, 60초, 세션 2026-10-20 04:55~):

```
started 2027  (33.8/s wall)   peak occupancy 90 / 96
hold median 2000 ms  (이 세션은 전부 CU 타임아웃. §18.4의 DU 조기 해제는 안 나타남)
gap p50 29 ms  p90 39 ms  p99 60 ms  max 108 ms   → 200 ms 이상 공백 0건
```

**죽은 시간은 없다.** 간격이 균일하므로 "버스트 사이에 멈춰 있다"는 가설은 기각된다.
96을 지속적으로 넘기려면 48/s가 필요하고, 사이클을 29 ms → 21 ms로 줄여야 한다.

### 19.1 사이클 분해 (`reproducers/rrc-signaling-storm/analysis/attempt_phases.py`)

JSONL의 각 이벤트가 벽시계(`t_ns`)와 공중(`air_ms`)을 모두 들고 있어 직접 분해했다.

| 구간 | 벽시계 | 공중 | 벽시계 비중 |
|---|---:|---:|---:|
| Msg3 → Msg4 | 22.8 ms | 30 ms | **79%** |
| Msg4 → retrigger | 3.6 ms | 10 ms | 13% |
| retrigger → 다음 Msg3 | 1.2 ms | 0 ms | 4% |
| 사이클 합 | 28.9 ms | 40 ms | 100% |

**Msg3→Msg4는 두 세션 모두 공중 30 ms로 동일하다**(이전 세션은 벽시계 100~113 ms, air/wall 0.29).
벽시계는 6배 차이인데 공중 값이 같으므로, 이 구간은 호스트 성능이 아니라 **공중 스케줄에 묶인
양자**다. 따라서 gNB 로그 수준을 낮춰도 줄어들지 않는다(그래서 시도하지 않았다).

### 19.2 시도한 6가지와 결과

| 변형 | 설정 | 시도율 | 점유 피크 | 판정 |
|---|---|---:|---:|---|
| 기준 | `RSS_ZMQ_TX_WAIT_US=100` | 33.8/s | 90 | — |
| 대기 20 µs | `=20` | 32.9/s | 91 | 동일 |
| 스핀 | `=-1` (`sched_yield`) | 26.7/s | 85 | **악화** |
| 조건변수 | `=-2` | 35.4/s | — | 동일 |
| ACK 게이트 해제 | `-g 0` | 34.1/s | — | 동일 |
| Msg4 대기 제거 | `-M 0 -G 0` | 181/s | **1** | **무효** |
| 코어 고정 | UE 2-7, odu 0-1 | 24.2/s | 51 | **악화** |

**대기 방식은 바꿔도 같다.** 굶음당 비용이 usleep(100) 288 µs, usleep(20) 240 µs, 조건변수 237 µs다.
조건변수는 이벤트 구동이라 폴링 지연이 0인데도 237 µs가 남는다 → 이 237 µs는 대기 방식 탓이 아니라
**생산자(UE L1)가 다음 샘플 블록을 만드는 데 실제로 걸리는 시간**이다. §18의 10 ms는 인위적 손실이
맞았지만, 남은 29초는 실제 작업이다.

**스핀은 역효과다.** 대기 적산이 28.5초 → 0.117초로 줄었는데 air/wall이 2.15 → 1.26으로 떨어졌다.
기다리는 대상인 생산자 스레드의 CPU를 빼앗는다. 유휴 코어가 6개여도 그렇다.

**`msg4_wait=0`의 음성 결과는 우리 버그였다**(정정 2026-10-26). 측정치 자체는 맞다: UE 10878건
시도에 **CU 컨텍스트 1건**(점유 피크 1). 그러나 원인은 "RA가 완료되지 않아 Msg3가 전달되지 않는다"가
아니다. 재시도를 `nr_rrc_ue_prepare_RRCSetupRequest()`에서 걸었던 것이 원인이다 — 그 시점의 Msg3
PUSCH는 아직 큐에만 있고, 재시도가 타는 `reset_ra()`의 memset이 **전송 전에** 그것을 지운다. 같은
파일의 게이트 (1) 주석이 이 기전을 이미 적어두고 있었는데(`269 attempts at the UE but only 93 Msg3
at the CU`), `msg4_wait=0` 경로에는 적용하지 않았다.

**`attempt_start`는 RRC의 페이로드 생성 이벤트지 전송 이벤트가 아니다.** 이번 건의 교훈은 Msg3를
건너뛸 수 없다는 것이 아니라, UE측 카운터 단독으로는 "공격이 닿았다"를 판정할 수 없다는 것이다.
판정은 `rss_poll()`의 RA 게이트로 옮겼다: `nrRA_WAIT_CONTENTION_RESOLUTION`은
`nr_Msg3_transmitted()`가 설정하는 상태이므로, 그 상태에 도달했다는 것은 Msg3 페이로드가 이미
PHY로 넘어갔다는 뜻이다.

**코어 고정은 이번에도 악화다**(§11.3의 결론과 동일). 10 ms 타임아웃이 사라진 뒤에도 그렇다.

### 19.3 결론: 단일 UE 천장은 약 35/s, 점유 90~91 / 96

사이클 40 ms 공중이 RA 절차의 고정 비용이고 UE가 줄일 수 있는 부분이 없다. 점유는
시도율 × 보유시간이며 보유 2000 ms는 gNB가 정한다. 따라서 단일 UE는 구조적으로
`(air/wall) / 0.040 × 2.0` 에 묶인다. 지속 포화에는 air/wall 2.0 이상을 사이클 내내 유지해야
하는데, 실측 사이클 내 유효 air/wall은 1.41이다(40 ms 공중 / 28.3 ms 벽시계).

### 19.4 2 UE — 상한 96/96 에 도달하지만 공유 라디오가 손상된 상태다

§18 이전에는 2 UE가 `Error, channel timeout` 후 어서션으로 **죽었다**. 수정 후에는 **죽지 않고
60초를 완주했다**(어서션 0건, SIGSEGV 0건). 다만 타임아웃 자체는 사라지지 않았다.
run `ZWtwo-052030Z`:

```
started 2316  (38.6/s wall, per-second max 72/s)
peak occupancy 96 / 96          ← 상한 도달
hold median 1999 ms
rrcReject                33     (같은 세션 단일 UE 0건)
"DU is not able to serve"  11   (단일 UE 0건)
rrcSetupComplete          8     (2316건 중, 0.3%)
NGAP InitialUEMessage     2

ue.log  "Error, channel timeout"  5136 건
air_per_wall                      1.08 ~ 1.09   (단일 UE 1.9~2.4)
```

용량 상한 96에 정확히 닿고 거절이 나온다. 단일 UE(점유 피크 90)는 상한 96에 닿지 않아
`rrcReject`가 0건이었으므로, **거절은 2 UE 에서만 관측됐다.**

다만 **공유 라디오는 손상된 상태로 동작한다.** `zmq_tx_stream::transmit()`은 `align()`이
타임스탬프 경과를 보고하면 `Error, channel timeout`을 찍고 **그 전송을 버린다.** 5136건이 찍혔고
air_per_wall 이 단일 UE의 절반 이하(1.09)로 떨어졌다. 평균 시도율이 2배가 아니라 1.14배인
(38.6 vs 33.8) 이유가 이것이다. "죽지 않았다"를 "정상"으로 읽지 않는다.

따라서 2 UE 결과는 **상한 도달의 증거로는 유효하지만, 처리량·타이밍 수치의 근거로는 쓸 수 없다.**
샘플 유실이 있는 런이다. 4 UE 로 넘어가기 전에 이 타임아웃을 먼저 줄여야 한다.

RRCSetupComplete 미전송형 순도는 99.7%다. `rrcSetupComplete` 8건은 §5의 정상 접속 유실과 같은 계열로 보이며 원인은
확인하지 않았다. 지속 포화(점유를 96에 **유지**)와 정상 단말 영향은 여전히 미확인이다.

## 20. 3 UE / 4 UE — 거절은 선형으로 늘지만 지속 포화는 아직 아니다

§19.4 의 2 UE 에서 3을 건너뛴 이유는 없었다. 이전 세션의 1/2/4 스윕 패턴을 그대로 물려온 것이고,
2 UE 가 이미 상한 96 을 쳤으므로 필요한 것은 **속도가 아니라 지속성**이었다. 3 과 4 를 모두 돌렸다.
지속성을 재려면 피크만으로는 부족해서 `cu_occupancy.py` 에 **수준별 체류 시간과 최장 연속 구간**을
추가했다.

### 20.1 결과 (각 60초, gNB 기본 설정, 환경 무변경)

| | 1 UE | 2 UE | 3 UE | 4 UE |
|---|---:|---:|---:|---:|
| run | `ZWS100-045539Z` | `ZWtwo-052030Z` | `ZWthree-054246Z` | `ZWfour-054420Z` |
| 시도율(평균) | 33.8/s | 38.6/s | 36.2/s | 37.4/s |
| 초당 최대 | 49/s | 72/s | 71/s | 92/s |
| 점유 피크 | 90 | 96 | **96** | **96** |
| `rrcReject` | 0 | 33 | 198 | **312** |

**시도율은 2 UE 부터 36~38/s 에서 평탄하다.** UE 를 늘려도 올라가지 않는다. 하나의 라디오와

깊어진다.

보였던 소수 누수(8건, 12건)도 사라졌다. 코어에는 단 한 건도 닿지 않았다.

### 20.2 지속 포화 측정 — 피크는 맞고 평탄 구간은 1초 미만

```
4 UE:  >= 48   56.4 s of 59 s ( 95%)   최장 연속 50.33 s
       >= 80   23.5 s of 59 s ( 40%)   최장 연속  1.37 s
       >= 90   17.4 s of 59 s ( 29%)   최장 연속  1.17 s
       >= 96   12.6 s of 59 s ( 21%)   최장 연속  0.93 s

3 UE:  >= 48   60.4 s of 60 s (101%)   최장 연속 26.62 s
       >= 96    8.4 s of 60 s ( 14%)   최장 연속  0.64 s
```

**상한 96 에는 전체 시간의 21% 동안 머문다. 그러나 한 번에 0.93초를 넘기지 못한다.**
즉 톱니 모양이고 평탄한 포화가 아니다. 용량의 절반(48) 이상은 **50.33초 연속** 유지되므로,
"절반 이상 점유"는 지속으로 보고할 수 있다.

### 20.3 톱니의 원인은 측정됐다 — 1초급 공백

| | 1 UE | 2 UE | 3 UE | 4 UE |
|---|---:|---:|---:|---:|
| 시도 간격 p50 | 29 ms | 24 ms | 15 ms | 10 ms |
| 시도 간격 p99 | 60 ms | 132 ms | **1046 ms** | **1040 ms** |
| 최대 간격 | 108 ms | 1077 ms | 1137 ms | 1159 ms |
| 200 ms 이상 공백 | **0건** | 3건 (3.1 s, 5%) | 22건 (23.4 s, 39%) | **25건 (26.7 s, 45%)** |

단일 UE 에는 200 ms 이상 공백이 **0건**이었다(§19). UE 를 늘리면 **1초가 넘는 멈춤**이 생기고,
4 UE 에서는 구간의 45%가 그런 공백이다. 보유 시간이 2초이므로 1초 멈추면 점유가 절반으로 빠진다 —
이것이 96 을 1초 이상 유지하지 못하는 직접적인 이유다.

공백 건수(0 → 3 → 22 → 25)와 채널 타임아웃(0 → 5k → 15k → 40k)이 같은 방향으로 움직인다.
`zmq_tx_stream::transmit()` 은 `align()` 이 타임스탬프 경과를 보고하면 전송을 **버린다**. 유실이
누적되면 RA 가 실패하고 그 UE 는 다음 기회까지 쉰다.

### 20.4 결론과 다음 레버

- **보고 가능**: 기본 설정 OCUDU 의 자원 상한 96 에 도달하고 `rrcReject` 312건,
  `DU is not able to serve the UE` 104건. 코어 미도달(NGAP 0). 4 UE, gNB 무수정·설정 기본값.
- **보고 불가**: 지속 포화. 96 최장 연속 0.93초.
- **다음 레버는 UE 수가 아니다.** 5·6 UE 로 늘려도 시도율은 36~38/s 에서 평탄하고 유실만 커진다.
  병목은 **공유 라디오의 샘플 유실**이다. `TRANSMIT_TS_ALIGN_TIMEOUT` 이 0 ms 로 하드코딩돼 있어
  (`zmq_imported.cpp`) 정렬이 조금만 늦어도 바로 버린다. 이 값을 늘리거나 UE 별 타임스탬프 정렬을
  고치는 것이 다음 단계다.
- 지속 포화가 확인되기 전까지 RRCSetupComplete 미전송형은 **탐지 검증 시나리오**이며, "마비"는 주장하지 않는다(§18.6).

## 21. 샘플 유실(`Error, channel timeout`) 원인 추적 — 가설 3개 실패, 구조 문제로 확인

§20.4 에서 "다음 레버는 `TRANSMIT_TS_ALIGN_TIMEOUT`"이라고 적었다. **틀렸다.** 세 가지를
시도해 모두 반증됐고, 마지막에 실측 진단으로 원인의 성격을 확인했다.

### 21.1 가설 1 — `TRANSMIT_TS_ALIGN_TIMEOUT` 이 0 ms 라서 (코드 읽기로 반증)

```c
bool zmq_tx_channel::align(uint64_t timestamp, std::chrono::milliseconds timeout)
{
  if (sample_count_ >= timestamp) {
    return sample_count_ > timestamp;   /* ← 여기서 리턴. timeout 을 쓰지 않는다 */
  }
  ...  /* timeout 은 sample_count_ < timestamp, 즉 "너무 이른" 경우에만 쓰인다 */
```

`transmit()` 은 `align()` 이 true 를 주면 `Error, channel timeout` 을 찍고 전송을 버린다.
그 true 는 **타임스탬프가 이미 지난 경우**에 첫 분기에서 나온다. 타임아웃 값과 무관하다.
빌드하지 않고 기각했다.

### 21.2 가설 2 — 공유 스트림에 단조 타임스탬프를 강제하면 된다 (실행으로 반증)

늦은 배치를 버리지 말고 현재 위치로 당겨 쓰게 했다(`RSS_SHARE_WR_MONOTONIC`).
4 UE, 60초, 같은 바이너리:

| | `=0` (원래) | `=1` (클램프) |
|---|---:|---:|
| run | `ZWmon0-060448Z` | `ZWmon1-060625Z` |
| 시도 | 2387 | **32** |
| `Error, channel timeout` | 21,178 | **0** |
| 플러시 | 140,000 | 180,000 |
| 클램프 | — | **179,997 (100%)** |
| 최악 지연 | — | **1,403,212,303 샘플** |
| air_per_wall | 0.873 | 1.638 |

타임아웃은 0이 됐지만 **시도가 2387 → 32 로 붕괴했다.** 클램프가 플러시당 `nsamps` 씩 자기
카운터를 올리는데, 이는 **슬롯당 플러시가 1회**라는 가정이었다. 실제로는 60초에 14~18만 회
플러시이고 슬롯은 약 12만 개다. 카운터가 실제 스트림보다 앞서 달아나 모든 쓰기가 먼 미래에
떨어졌다. 기본값 0 으로 되돌리고 음성 결과로 코드에 남겼다.

### 21.3 실측 진단 — 순서 역전은 8%, 유실은 17%

클램프 없이 "직전 배치보다 과거인 타임스탬프"만 세도록 바꿨다(노브와 무관하게 항상 계측).
run `ZWdiag-060934Z`, 4 UE, 60초:

```
attempts          2202
Error, channel timeout  23,322
shared TX: 140000 flushes, 11284 out of order (8.06%, worst 34560 samples back), 0 clamped
air_per_wall      0.990
```

**순서 역전은 전체 배치의 8%인데, 유실은 17%다.** 역전이 유실의 절반밖에 설명하지 못한다.
게다가 역전된 배치가 반드시 버려지는 것도 아니다(장치의 `sample_count_` 와의 관계에 달려 있다).

나머지 절반은 `align()` 의 **영(zero) 패딩**이 유력하다. 배치가 이르면(`sample_count_ < timestamp`)
`align()` 은 영을 채우고 `sample_count_ = timestamp` 로 **점프**한다. 그러면 다른 UE 가 더 낮은
타임스탬프로 제출한 다음 쓰기는 과거가 되어 버려진다. 즉 한 UE 가 스트림을 앞으로 끌면 다른
UE 가 밀린다. "최악 34,560 샘플 뒤"는 슬롯 두 개 분량 정도다.

### 21.4 결론: 한 줄 수정이 아니라 설계 긴장이다

장치는 공유 스트림 **하나**에 `sample_count_` **하나**를 갖는다. 그런데 N 개 UE 는 각자
독립적인 시계로 돌고, `rss_shared_read` 는 **UE 별 커서**로 각자가 요청한 만큼을 준다. 커서가
벌어지면 타임스탬프가 벌어지고, 공유 TX 는 그것을 순서대로 받아들일 수 없다.

- **UE 별 커서는 되돌릴 수 없다.** 라운드 방식이 호출자 요청 수와 다른 개수를 반환해
  `nr-ue.c:714` 의 `unitTransfer == res` 어서션을 깨뜨렸다(§18 이전 기록).
- 올바른 방향은 **읽기 측에서 UE 들을 서로 묶어두는 것**이다(가장 느린 UE 기준으로 전진 폭을
  제한). 한 UE 가 멈추면 전체가 멈추는 교착 위험이 있어 상한·타임아웃 설계가 필요하다.
- 그 작업 전까지 **4 UE 결과는 §20 그대로 유효하다**(상한 96 도달, `rrcReject` 312,
  RRCSetupComplete 미전송형 순도 100%). 다만 톱니이고 처리량 수치는 유실 때문에 근거로 쓸 수 없다.
