# DU 포화 목표 — 최종 기록 (2026-10-29)

목표: DU UE context cap 96(기본 설정)에서 DU RRC signaling storm으로 정상 UE 연결 불가 재현.
결론: **96 피크는 재현되지만 유지 불가. 수락률이 44.9/s에 4% 부족하고, 이를 메울 코드가
현재 빌드에 없다.** 설정은 바꾸지 않고 기존 자원·설정으로 측정했다.

## 확인된 구조

- DU의 병목 자원은 **UE context + 전용 SR/CSI = 96**(CU-CP 한도 8,192와 무관).
- 컨텍스트 수명: RRC Setup Procedure started → UE Removal Routine finished (T_slot ≈ 2.14초).
- **거절(rrcReject)은 점유 96에서만 발생**한다(이전 세션 원본 로그 분석).
- 점유 유지 조건: 수락률 ≥ 96 / 2.14 = **44.9회/초**.

## 실측 (설정 변경 없이, 120초 런)

| 구성 | 수락률 | 최대 점유 | 96 이상 누적 |
|---|---|---|---|
| 2 UE | 32.2/s | 96 | 0.11 s |
| 4 UE | 38.6/s | 96 | 0.01 s |
| 4 UE `-r 0` | **43.0/s** | 96 | 0.01 s |
| 5 UE `-r 0` | 42.6/s | 96 | - |
| 6 UE `-r 0` | 38.7/s | 96 | - |
| 4 UE `RA_DEPTH=4` | 41.8/s | 96 | 0.03 s |
| 4 UE `RA_GATE=0` | 42.3/s | 96 | 0.03 s |
| 4 UE `GATE_TIMEOUT_MS=50` | 42.5/s | 96 | - |

- 최고 43.0/s. 필요 44.9/s 대비 **+1.9/s(4.4%) 부족**.
- UE 수를 늘리면 오히려 감소(4→6 UE: 43.0→38.7). 공격 노브 조합으로도 43/s가 상한.

## 왜 4%를 못 메우는가 (점검 완료)

1. UE 수: 이미 소진(역효과).
2. 거부 백오프 해제(`-r 0`): +11% 확보, 적용 완료.
3. RA 병렬화(`RA_DEPTH`): 노브는 있으나 풀 구현(`ra_pool`, `RA_config_t *ra`,
   `rss_ra_alloc`)이 현재 트리에 없어 무효.
4. archive 패치(`rss-ue-full-20261023.patch`) 이식: `rrc_proto.h` Hunk#1,
   `rrc_timers_and_constants.c` Hunk#1/#3 충돌(우리 probe pacing 패치와 충돌).
   약 10개 파일(타이머 인자·포인터 전환) 수동 이식이 필요하고, 패치는 당시
   "결선 완료, 측정 전"이었다.
5. gNB/CU 설정 변경: 사용자 지시로 금지.

## 정상 UE 거부에 대해

- 점유가 96에 붙지 않으므로(평균 약 92) 정상 UE는 빈 슬롯에 접속한다.
- 이전 세션 실측: 프로브 첫 시도 연결, 지연 75→180 ms(2.4~2.8배). 거부 아님.
- archive 결론과 일치: 용량 경로 상한 93.4/96, "거절은 천장에서만".

## 결론

- **기존 설정·현행 도구로 "96 유지 + 정상 UE 거부"는 불가능**하다.
- 96 피크(순간 접촉)와 평균 92, 천장에서만 거절이 재현 가능한 최대치다.
- 다음 단계는 코드 작업이다: RA pipelining 이식(4% 확보 목표) 또는 evict/harvest 경로
  (C-RNTI 수확 커버리지 1/3 한계 기록됨). 둘 다 새 브랜치·빌드·측정이 필요하다.
