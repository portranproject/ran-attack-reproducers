# 최장 공백의 기전: 거절은 점유 96에서만 일어난다

2026-10-21. `artifacts/verify-20261021/ocu-window-raw.log`(가공 없는 원본) 분석.

## 핵심

**거절(`Sending rrcReject`)의 100%가 점유 정확히 96 — 천장 — 에서 발생한다.**

조건은 점유 계산 정의다. OCUDU의 컨텍스트 수명은
`"RRC Setup Procedure" started` → **`"UE Removal Routine" finished successfully`**이고,
`"RRC Setup Procedure" timed out`이 아니다. 해제는 `UE Context Release Routine` →
`UE Removal Routine`으로 **비동기 2단계**라, 타임아웃 로그 시점에 슬롯은 아직 안 풀린다.

| 점유 정의 | 피크 | 평균 | 거절이 천장에서 일어난 비율 |
|---|---|---|---|
| `timed out` 기준 | 96 | 73.6 | **40%** |
| `removal 완료` 기준 | 96 | 79.3 | **100%** |

(verify 창: 2 UE, 120.4초, 수락 37.0/s, 실제 거절 5건)

## 목표의 정확한 재진술

> **"최장 공백 < 100 ms" ≡ "점유가 96 아래로 100 ms 넘게 떨어지지 않는다"**

거절은 천장에서만 나오므로 거절 간 공백은 **천장 아래에 머문 시간**이다.
즉 이 지표는 "공격 세기"가 아니라 **"천장 밀착 지속성"**을 재고 있다.

## 요구량 — 이전 추정 2건을 정정한다

`평균점유 = 수락률 x T_slot`, `T_slot` = started → removal 완료.

verify 창 실측: `79.3 / 37.0 = ` **T_slot ≈ 2.14 s** (보유 2,000 ms + 비동기 해제 ~140 ms).

점유 96 고정 조건: 수락률 ≥ `96 / 2.14 =` **44.9/s**.

| 추정 | 값 | 근거 | 평가 |
|---|---|---|---|
| 초기 | 도착 148/s (2.5배) | 거절 100/s 필요 + Poisson 가정 | **틀림** — 거절을 Poisson으로 가정 |
| 중간 | 수락 48/s (+12%) | `96 / 2.0s` | 틀림 — T_slot 을 보유시간 2.0s 로 봄 |
| **실측** | **수락 44.9/s (+5%)** | `96 / 2.14s`, T_slot 실측 | 현재 6 UE 42.9/s |

**필요한 것은 수락률 +5%다.**

## 반증한 가설 2건

1. **배치 해제 가설** — "보유 만료가 덩어리로 와서 용량이 한꺼번에 열린다".
   반증: 최장 공백 8개에서 공백 중 점유가 67~86으로 **천천히** 변하고 급락이 없다.
2. **도착 버스트 가설** — "인스턴스가 lockstep 으로 동기화돼 도착이 뭉친다".
   반증: **최장 공백 1,130 ms 동안 수락이 46.9/s로 전체 평균 42.9/s보다 높다.**
   도착은 멈추지 않는다. gNB 가 거절할 이유가 없어서(천장 아래라서) 안 한 것이다.
   도착 CV는 2.04로 실제로 뭉쳐 있지만, 그게 공백의 원인은 아니다.

## 다음 측정 (이것이 다음 액션)

지금까지의 CU 로그 수집이 **RRC 줄만 필터**해서 `UE Removal Routine`이 빠져 있었다
(`artifacts/modeA-peak-6ue-20261021/ocu-6ue-rrc-lines.log`). 그래서 6 UE 최선 런의
**올바른 정의 점유를 모른다.**

필요한 런: 인스턴스 수 6/7/8, **CU 로그 전체 수집**, 지표는

- 수락률 (목표 ≥ 44.9/s)
- 평균 점유, **점유 96 체류 시간 비율**
- **점유가 96 아래로 떨어진 최장 구간** ← 이게 진짜 목표 지표

8 UE 는 과거에 "공백 2,380 ms"로 더 나빴다고 기록됐으나, 그때의 **수락률은 기록되지 않았다.**
수락률이 올랐는데 공백이 나빠졌다면 원인은 따로 있다.

# 실측 2라운드 (2026-10-21 11:00~11:21)

## gNB 거동: 천장에서 수락이 붕괴한다

`c_u6` 정상상태 창(56.9초)에서 점유 구간별 CU 거동:

| 구간 | CU 수락/s | CU 해제/s | 거절/s |
|---|---|---|---|
| **천장(96) 체류** | **1.0~3.4** | 30~45 | **23~37** |
| 하락 중 | 36~56 | 39~61 | ~0 |

천장에 닿으면 gNB는 수락을 거의 멈추고 들어오는 것을 거의 다 거절한다.
그런데 해제는 계속되므로 점유가 net ~39/s로 급락해 96 → 75~86까지 파인다.
**이력현상(hysteresis)이고, 천장 체류가 1초를 못 넘기는 이유다.**

하락 중 해제율(40~61/s)은 **2.14초 전 충전기의 수락률의 메아리**다.
충전기에 수락이 몰리면 2.14초 뒤 해제가 몰려 들어와 현재 도착을 앞지른다 →
자기 유지 진동. 주기 ≈ 체류 + 하락 ≈ 2~2.5초.

## 소진된 UE 측 레버 (모두 실측)

| 레버 | 결과 | 근거 |
|---|---|---|
| RA 파이프라인 K=2 | 반증 | CU 컨텍스트 2,492 vs 2,505 (−0.5%) |
| 인스턴스 수 6→8 | 무효 | 수락 41.3 vs 40.9/s, 천장미달 2,513 vs 2,812 ms |
| lockstep 창 1→4슬롯 | 무효 | 수락 42.0/s, 천장미달 2,327 ms |
| `target_occupancy` 100/104/112 | **비활성** | `occ_hold=0` 전부 |

**`target_occupancy`가 비활성인 이유**: `nr_rss_occupancy()`는 "최근 `hold_ms` 내
Msg5 생략 수"를 센다. 실현 msg4 37/s x 2.14s = 추정 점유 ~79로 목표 100에 닿지 않는다.
즉 이 노브는 **상한(throttle)이며 하한(pin)이 아니다** — 도착 부족으로 생긴 공백을
고칠 수 없다. 코드 주석의 묵은 근거("interval_ms 단독 불가, Msg4 3.8/s 포화")는
단일 UE 시절 측정이라 6 인스턴스 체제와 무관하다.

**반증된 가설**: "거절당한 인스턴스가 백오프에 묶여 도착이 끊긴다" —
거절→재시도 지연 실측 p50 **19 ms**, p90 21 ms, max 25 ms. 회복은 즉각적이다.

## 지표 주의 2건

### 1. 거절-간-공백 지표는 조작 가능하다

`t_o100`: 거절 간 공백 최장 **137 ms**(목표 근접) — 그런데 거절이 57초에 11건뿐,
천장 체류 0.9%, 천장미달 최장 54,475 ms. **공격이 실패했는데 지표가 좋아 보인다.**

거절이 희박하면 "존재하는 거절들 사이의 간격"만 재므로 의미가 없다.
정직한 지표는 **천장 체류율과 천장미달 최장을 함께** 보는 것이다.
기존 1,130 ms는 건강한 런(천장 체류 17%)에서 나온 값이라 비교가 성립했다.

### 2. 세션 내 점진 저하 — 스윕 간 비교 무효

동일 설정(6 UE, lockstep 1슬롯)의 시간에 따른 변화:

| 시각 | 수락/s | 평균점유 | 천장체류 |
|---|---|---|---|
| 11:00 (`c_u6`) | 41.3 | 90.7 | 16.9% |
| 11:13 (`twarm`) | 32.7 | 71.4 | 7.2% |
| 11:21 (`t_o112`) | 31.7 | 70.2 | 13.1% |

~20분 만에 수락률이 23% 떨어졌다. 원인 미규명(CU 로그 비대, 누적 상태 의심).

**프로토콜 교정**: 대조군은 반드시 **같은 배치 안에서** 돌려야 하고,
스윕 간 수치를 직접 비교하면 안 된다. 긴 세션에서는 CU 재시작으로 기준을 복구한 뒤
대조군을 다시 측정할 것.

이 저하는 "수락 42/s가 gNB 하드 상한"이라는 해석도 약화시킨다 —
저하된 상태의 32/s와 신선한 상태의 42/s 중 어느 쪽도 상한의 증거가 아니다.
상한 주장은 **신선한 기준에서 부하를 올려가며** 재확인해야 한다.

# 인과 사슬 확정 + 위상 분산 실패의 진짜 원인 (2026-10-22, 오프라인 분석)

박스 비용 없이 기존 로그(`artifacts/modeA-peak-6ue-20261021/ocu-6ue-rrc-lines.log`,
6 UE·lockstep 1슬롯·55.4초·거절 654건)만으로 판정했다.

## 공백을 만드는 것은 파인 깊이이고, 깊이를 만드는 것은 해제 뭉침이다

| 상관 | r | 기울기 |
|---|---|---|
| 체류 길이 → 파인 깊이 | **+0.05** | — (무상관) |
| 체류 중 거절 수 → 깊이 | +0.13 | — |
| **파임 중 해제 수 → 깊이** | **+0.60** | +0.17 슬롯/해제 |
| 파임 중 수락 수 → 깊이 | +0.43 | — |
| **깊이 → 공백 길이** | **+0.44** | **+36 ms/슬롯** |

| 파인 깊이 | n | 평균 공백 | p90 |
|---|---|---|---|
| 0~2 슬롯 | 84 | **75 ms** | 169 |
| 2~5 | 235 | 131 | 314 |
| 5~10 | 41 | 196 | 501 |
| 10~20 | 4 | 904 | 1047 |

깊이 ≤1 슬롯인 공백은 평균 73 ms이고 **79%가 100 ms 이하**다.
파임 중 해제가 0~3건이면 평균 공백 **49 ms**, 30건 이상이면 847 ms.

**사슬**: 생성 버스트 → (2.14초 뒤) 해제 버스트 → 깊은 파임 → 긴 공백.
도착 CV는 2.04(10 ms 내 최대 5건 뭉침)이고, **생성 버스트는 UE가 통제한다.**

→ 목표는 "더 많이 보내기"가 아니라 **"고르게 보내기"**로 환원된다.
   정량 조건: 파임당 해제를 3건 이하, 즉 파인 깊이를 1~2 슬롯으로 억제.

## 반증: 짧은 거절 백오프

체류 길이와 공백의 상관이 r=−0.00~+0.07(묶음 임계 50/100/150 ms 전부).
체류가 0~20 ms였든 150~400 ms였든 평균 공백은 ~170~230 ms로 같다.
**천장 체류를 끊어도 파임이 줄지 않는다** → 박스를 켜지 않고 폐기.

## 정정: 위상 분산(`RSS_PHASE_STAGGER`) 실패의 원인

코드 주석(`main_ue_nr.c`)과 이전 기록은 원인을
"`rss_flush_locked`가 `wr_joined >= n_ue` 만장일치를 기다려 유휴 인스턴스가
배치를 영구히 막는다"로 적었다. **틀렸다.**

실제 범인은 `nr-ue-ru.c` 쓰기 경로의 late-drop 가드다.

```c
if (s->wr_emitted_set && timestamp < s->wr_emitted_end) { s->wr_late_drop++; return nsamps; }
```

위상을 흩뜨리면 인스턴스들이 서로 다른 타임스탬프로 쓴다. 먼저 쓴 인스턴스가
`wr_emitted_end`를 전진시키면, 더 이른 타임스탬프로 쓰는 나머지는 전부 late-drop된다.
(만장일치 배리어는 교착이 아니다 — 다른 키가 오면 위쪽 분기가 즉시 flush한다.
 다만 배치가 1건으로 쪼개져 합산이 무너진다.)

그리고 이건 **고칠 버그가 아니라 설계상 필연**이다. N 인스턴스가 하나의 ZMQ
스트림을 공유해 신호가 합산되려면 같은 타임스탬프여야 한다. 장치는 단조
증가하는 타임스탬프만 받는다. **라디오 쓰기 시각을 흩뜨리는 위상 분산은
공유 라디오와 원리적으로 양립할 수 없다.** late-drop 자체는 유효한 수정이다
(`ch.timeout` 409/s → 3/s, 역순 6.95% → 0.08%).

## 남은 단 하나의 레버 (미시험)

분산해야 할 것은 **라디오 쓰기 시각이 아니라 PRACH 기회 선택**이다.
모든 인스턴스가 매 슬롯 같은 타임스탬프로 쓰되, MAC에서 인스턴스별로
다른 PRACH 기회를 고르게 한다. 기회 사용률이 34%뿐이라 자리가 있다
(여유 3배). 이는 `nr_ra_procedures.c`의 기회 선택부 변경이며
공유 라디오 설계를 건드리지 않는다.

예상 효과: 10 ms 프레임 내 기회가 3~4개면 인스턴스 간 ~2.5 ms 분리 →
"10 ms 내 5건 뭉침"이 10 ms에 걸쳐 펴진다 → 도착 CV 하락 →
2.14초 뒤 해제도 펴짐 → 깊이 감소 → 공백 감소.

**미확인**: 실제 기회 수/배치, 2.5 ms 분리가 해제 뭉침을 3건 이하로
낮추기에 충분한지(해제 지연 분산이 이미 뭉침을 섞어놓을 수 있다).
검증에는 박스 1배치(약 10분)가 필요하다.

## 현재 결론

**목표 미달.** 최장 공백 2,327~2,812 ms(정상상태, 6·8 UE), 목표 100 ms.
단 p50은 이미 53~70 ms이므로 깨지는 것은 평균이 아니라 꼬리다.
꼬리는 해제 뭉침에서 오고, 해제 뭉침은 생성 뭉침의 메아리이며,
생성 뭉침만이 UE 측에서 통제 가능한 양이다.

# 레버 확정: 생성 위상 분산, 분리 간격 > 18 ms (2026-10-22, 오프라인)

## 메아리는 거의 완벽하다 — 앞선 "약한 메아리"는 내 측정 오류였다

`ocu-6ue-rrc-lines.log` (6 UE, 55.4초):

- **컨텍스트 수명 1,999.4 ms ± 0.3 ms** (p01 1998.9 / p99 1999.9) — gNB 보유시간은 사실상 상수
- **생성→해제 교차상관 지연 2,000 ms 에서 r = +0.99** (100 ms 빈)
- 생성 간격 CV 2.04, 해제 간격 CV 2.05 — 버스트성이 1:1 전달

**해제는 생성의 2.0초 지연 복사본이다.** 따라서 생성을 고르게 하면 해제도 고르게 된다.

앞서 기록한 "2.14초 전 수락 → 파인 깊이 r=+0.16"은 **창을 2.14초에 맞춘 탓**이다.
같은 데이터에서 2.0초 지연은 r=+0.99, 2.1초 지연은 −0.19다. 메아리가 날카로워서
100 ms만 빗나가도 상관이 사라진다. 정정한다.

## 다만 수락 슬롯은 제거 완료에 풀리고, 그 지연이 번진다

`verify-20261021/ocu-window-raw.log` (n=4,381):

| 구간 | p50 | 평균 | 표준편차 | p01~p99 |
|---|---|---|---|---|
| timed out → removal 완료 | 151.5 | 154.4 | **17.6** | 124.7~223.6 ms |
| started → removal 완료 (= T_slot) | 2,150.9 | **2,153.8** | 17.6 | 2,124~2,223 ms |

거절은 제거 완료 기준 점유 96에서만 나오므로, 통제해야 할 것은 **제거 완료 시각**의
균일성이다. 그 번짐이 **±17.6 ms**다.

## 정량 설계 조건

**생성 간 분리 간격 > ~18 ms.** 그보다 촘촘하면 제거 지연 번짐에 뭉개진다.

이 조건이 두 가지를 결정한다.

1. **PRACH 기회 분산(프레임 내)은 무효다.** 10 ms 프레임에 기회 3~4개면 분리 ~2.5 ms로,
   번짐의 1/7이다. 앞 절에서 "남은 단 하나의 레버"로 적은 것을 **철회한다.**
2. **올바른 레버는 RA 시작 시점의 인스턴스별 위상 오프셋이다.**
   수락 42/s ≈ 24 ms/건, 인스턴스 6개가 각자 ~140 ms 주기 → `140/6 ≈ 23 ms` 간격.
   23 ms > 18 ms 이므로 번짐을 넘어 살아남는다.

## 수정 설계

기동 시 **한 번** 인스턴스 `i`의 첫 RA 시도를 `i x (cycle_ms / n_ue)`만큼 늦춘다.
이후 모든 인스턴스가 같은 주기로 돌므로 분리가 유지된다.

- 계층: RRC 재시도 경로(`rrc_timers_and_constants.c`), **라디오 계층 아님**
- 모든 인스턴스는 여전히 매 슬롯 **같은 타임스탬프**로 쓴다 → late-drop 가드와 충돌 없음.
  이것이 refuted 된 `RSS_PHASE_STAGGER`(라디오 쓰기 위상 분산)와 **다른 점**이다
- 노브: `RSS_START_STAGGER_MS` (0 = 현행). 자동이면 `cycle_ms / n_ue` 추정값 사용

## 예상 효과와 미확인

생성 23 ms 등간격 → 해제도 23 ms 간격(±18 ms 번짐) → 파임당 해제 수 감소 →
파인 깊이 1~2 슬롯 → 공백 평균 73~75 ms, 100 ms 이하 비율 79%.

**미확인**: (a) 인스턴스 주기가 실제로 균일한지(측정된 `cycle_p50`은 70 ms인데
도착 42/s·6 인스턴스면 143 ms여야 하므로 주기 정의를 확인해야 한다),
(b) 천장에서 gNB가 일괄거절로 들어가는 동역학이 균일 도착에서도 진동할지,
(c) 오프셋이 ZMQ lockstep 배리어의 라운드 진행과 간섭하지 않는지.

검증에는 박스 1배치(대조 + 오프셋 0/12/23/46 ms, 약 10분)가 필요하다.

## 현재 상태

**목표 미달.** 최장 공백 2,327~2,812 ms 대 목표 100 ms.
이 레버는 설계 조건(>18 ms 분리)과 기전(r=+0.99 메아리)이 모두 실측으로 뒷받침되는
첫 번째 후보다. 그 전의 후보 7개는 전부 실측 반증 또는 무효였다.

# 레버 재확정: 기회당 1 인스턴스 중재 (2026-10-22, 오프라인)

## 앞 절의 설계 조건을 완화한다

앞서 "생성 간 **분리 간격** > 18 ms"라고 적었다. **과한 조건이었다.**
번짐이 상쇄되려면 필요한 것은 간격의 크기가 아니라 **지터가 번짐보다 작은 것**이다.

- 수락 44.9/s → 평균 간격 **22.3 ms**
- PRACH 기회 격자 **10 ms** (실측: `Selected RO Frame N, Slot 19, Symbol 0, Fdm 0` — 매 프레임 1회, FDM 1개)
- 10 ms 격자에서 20·30 ms를 섞으면 평균 22.3 ms, **지터 ±5 ms ≪ 번짐 17.6 ms**

즉 격자 자체는 장애물이 아니다. 필요한 기회 점유율은 **45%**(22.3 ms에 1건 ÷ 10 ms)뿐이다.

## 진짜 문제: 기회를 공유하며 뭉친다

4 UE 600초 실측 (`modeA-sustained-20261021/attempts.jsonl`, 31,504 시도):

| 항목 | 값 |
|---|---|
| 인스턴스별 시도율 | 13.1/s (4개 모두) |
| 인스턴스별 주기 p50 | 69.3 ms, **CV 0.50~0.63** |
| 인스턴스 위상 집중도 R | **0.01~0.02 (이미 무작위)** |
| 전체 도착 간격 p50 | 10.7 ms |
| **1 ms 내 동시 도착** | **35.3%** |
| 18 ms 미만 간격 | 60.0% |

위상이 이미 무작위라 **고정 시작 오프셋은 무의미하다**(앞 절의 `RSS_START_STAGGER_MS`
설계를 철회한다). 동시 도착 35.3%는 위상 무작위성으로 설명되지 않는다 —
4 인스턴스·69 ms 주기에서 1 ms 동시 확률은 ~6%여야 한다. 6배 초과다.

원인은 **기회 격자 공유**다. 한 기회에 준비된 인스턴스가 모두 함께 쏘고,
다음 기회는 비운다. 자리는 남는데(점유율 45%만 필요) 뭉쳐서 쓴다.

## 설계: 기회 중재

**한 PRACH 기회에 최대 1개 인스턴스만 프리앰블을 전송한다.**

- 인스턴스들은 이미 `rss_share` 뮤텍스를 공유한다(`nr-ue-ru.c`) → "이 기회를 점유한다"는
  클레임을 둘 자리가 있다. 라운드로빈 또는 선착순 + 다음 기회로 밀기
- 라디오 쓰기 타임스탬프는 **건드리지 않는다** → late-drop 가드와 충돌 없음
  (반증된 `RSS_PHASE_STAGGER`가 깨진 지점)
- 노브: `RSS_RO_ARBITRATE` (0 = 현행)

예상: 생성 간격이 10/20/30 ms 중 하나로 고정, 동시 도착 0% →
지터 ±5 ms ≪ 번짐 17.6 ms → 해제도 펴짐 → 파인 깊이 1~2 슬롯 →
공백 평균 73~75 ms, 100 ms 이하 79% (깊이-공백 관계 36 ms/슬롯에서 역산).

**미확인**: (a) 기회를 양보한 인스턴스의 주기가 10 ms 늘어 총 시도율이 떨어지는데,
그만큼 뭉침이 줄어 수락률이 오를지는 상쇄 관계라 측정이 필요하다.
(b) 천장에서 gNB 일괄거절 동역학이 균일 도착에서도 진동할지.
(c) 중재가 lockstep 배리어 라운드와 간섭할지.

검증: 박스 1배치(대조 + 중재 ON, 약 10분).

## 부수 발견: 거절도 컨텍스트를 쓴다

모드 B 용량 선언 원문:

> The upper-bound on the number of UEs supported by cell is 12 ... determined by
> the lowest of: **SR (12)**, CSI (96), SRS (n/a), UE contexts per cell (1984).

  천장에서 수락이 1~3/s로 붕괴하면서 거절이 23~37/s로 치솟는 이력현상은

# 조건식의 세 항을 분해한 결과 (2026-10-22)

천장 고정 조건: **수락률 × T_slot ≥ 천장**

| 항 | 실측 | UE 통제 가능? |
|---|---|---|
| 천장 | 96 | ✗ DU 선언 용량. 낮추려면 정상 접속 UE로 예산 선점 → `uicc1~5` + **코어 가입자 신규 등록** 필요(도구 밖) |
| 수락률 | 41.4~42.6/s (13개 설정, 3% 밴드) | ✗ 무엇을 바꿔도 불변 |
| **T_slot** | **2,154 → 2,197 ms (부하에 따라 증가)** | **△ 부분적으로 가능** |

## T_slot 은 부하에 민감하다

| 부하 | 수락/s | 거절로그/s | 제거지연 평균 | 표준편차 | p90 | T_slot |
|---|---|---|---|---|---|---|
| 2 UE (`verify-20261021`) | 30.5 | 0 | 154.4 | 17.6 | 174.3 | 2,154 ms |
| 6 UE + 중재 (`final_arb`) | 42.5 | 18.4 | **197.1** | 39.5 | **263.6** | **2,197 ms** |

필요값 `96 / 42.5 =` **2,259 ms**. 현재 2,197 ms → **부족 62 ms (제거지연 +31%)**.

고부하의 제거지연 **p90 263.6 ms는 이미 필요값 259 ms를 넘는다.** 평균이 못 따라올 뿐이다.

## 자기강화 기전

모드 B 용량 선언 원문: *"Up to 76 UE contexts can be created in the cell,
**the extra ones being used to RRC Reject UEs**."*

→ **거절도 컨텍스트를 만들고 철거한다.** 철거 부하 = 수락 42.5/s + 거절 15.3/s = 57.8/s.
→ 철거 부하 ↑ → CU `app_exec` 큐 ↑ → 제거지연 ↑ → T_slot ↑ → 평균점유 ↑ →
   천장체류 ↑ → 거절 ↑ (양의 되먹임)

실측이 이 고리를 뒷받침한다: 저부하 대비 고부하에서 제거지연 +42.7 ms.

## 막힌 지점

되먹임을 돌리려면 거절률을 올려야 하고, 거절은 천장에서만 나므로 도착률을 올려야 한다.
그런데 도착률도 ~61/s에서 막혔다.

| 인스턴스 | 중재 | UE 시도/s | 거절(CU)/s |
|---|---|---|---|
| 6 | ON | 61.3~62.7 | 14.5~16.3 |
| 8 | ON+RR | 60.5 | 15.9 |
| 10 | ON+RR | 58.1 | 13.5 |

인스턴스를 늘려도 도착률이 오르지 않는다(ZMQ 공유 한계, 8·10 UE 런은 창이 49~56초로
조기 종료되기도 했다). 기회 중재는 프레임당 1건 = 100/s까지 허용하므로 중재가 한계가 아니다.

## 현재 결론 — 미달이지만 거리가 수치화됐다

**목표 미달.** 최장 공백 최선 **621 ms**(중재 ON, 60초), 120초 본 런 1,018 ms, 목표 100 ms.

닫으려면 **둘 중 하나**다.

1. **제거지연 +31%** (197 → 259 ms). 거절률을 올려 CU 철거 부하를 깊게 하면 되는데,
   거절을 올리려면 도착률이 필요하고 도착률이 ~61/s에서 막혀 있다.
   → ZMQ 공유의 도착률 상한을 올리는 것이 다음 과제. (실 SDR OTA 경로는 미시험)
2. **수락률 +2.4/s** (42.5 → 44.9). 13개 설정에서 불변이었다.

즉 "도달 불가"가 아니라 **"남은 거리가 제거지연 62 ms 또는 수락률 2.4/s이고,
둘 다 도착률 상한에 묶여 있다"**가 정확한 현황이다.

# 최종: 꼬리는 제거지연 지터에 지배되고, 그 요구가 부하 요구와 상충한다

중재 적용 런(`final_arb`, 120초)의 CU 측 재분석. 기전은 중재 후에도 유지되며 더 강하다.

| 상관 | 중재 전 (6 UE) | **중재 후** |
|---|---|---|
| 파인 깊이 → 공백 | r=+0.44, 36 ms/슬롯 | **r=+0.64, 29 ms/슬롯** |
| 파임중 해제 → 깊이 | r=+0.60 | **r=+0.73** |

| 파인 깊이 | n | 평균 공백 |
|---|---|---|
| 0~2 슬롯 | 240 | **55 ms** (목표 충족) |
| 2~4 | 107 | 108 ms |
| 4~7 | 222 | 162 ms |
| 7~12 | 143 | 275 ms |

## 역산: 필요한 지터

공백 100 ms → 깊이 ≤ `100/29 =` **3.5 슬롯** → 한 파임에 해제 ≤3건.
해제는 생성의 2.0초 지연 복사본이고 생성은 중재로 10 ms 격자에 놓였으므로,
제거지연 지터 σ의 ±σ 창에 들어오는 생성 수가 곧 해제 뭉침 크기다.

`2σ/10ms ≤ 3.5` → **σ ≤ 17 ms**.

## 상충 — 두 요구가 같은 변수의 반대 끝을 가리킨다

| 부하 | 수락/s | 평균점유 | 제거지연 평균 | **σ** | 결과 |
|---|---|---|---|---|---|
| 저부하 (2 UE) | 30.5 | ~65 | 154.4 ms | **17.6 ms** | σ는 충족, 그러나 천장에 거의 닿지 않음 |
| 고부하 (6 UE+중재) | 42.5 | 93.4 | 197.1 ms | **39.5 ms** | 천장 체류 27.8%, 그러나 σ가 2.3배 초과 |

- 평균점유를 96에 올리려면 **부하를 올려야** 한다 → σ 39.5 ms → 깊이 ~8 → 공백 230~280 ms
- 깊이 ≤3.5를 얻으려면 **σ ≤17 ms**가 필요하다 → 저부하 값 → 평균점유 65 → 천장 미접촉

**필요 σ 17 ms는 저부하 실측 17.6 ms와 일치하고, 그 부하에서는 천장에 닿지 못한다.**
두 요구는 CU 부하라는 하나의 변수를 통해 반대 방향으로 당긴다.

σ와 `부하 → σ` 관계는 모두 **CU 구현 측 양**이다(비동기 2단계 해제의 `app_exec` 큐).
UE 측에서 둘을 분리할 수단은 이 세션에서 찾지 못했다.

## 잔여 뭉침의 위치가 이동했다

중재 후에도 CU 측 생성의 37.6%가 1 ms 내 동시다(생성 간격 p50 11.0 ms = 10 ms 격자와 일치).
중재는 **PRACH**를 기회당 1건으로 제한하지만 **Msg3 → 컨텍스트 생성**의 CU 측 배치 처리는
제한하지 않는다. 해제 간격은 61.3%가 동시다.
→ 잔여 뭉침은 PRACH가 아니라 CU 처리 단계에 있고, UE 통제 밖이다.

## 최종 현황

**목표 미달.** 최선 **621 ms**(중재 ON, 60초), 120초 런 1,018~1,297 ms, 목표 100 ms.
달성한 개선은 p90 **370 → 232~283 ms**, 최장 **2,640 → 621~1,018 ms**.

닫히지 않는 이유가 세 층으로 모두 측정됐다.

1. **천장 96** — DU 선언. 낮추려면 코어 가입자 신규 등록 필요(도구 밖)
2. **수락률 41.4~42.6/s** — 13개 설정 3% 밴드, 필요 44.9/s
3. **제거지연 σ** — 필요 ≤17 ms vs 천장 접촉에 필요한 부하에서 39.5 ms (상충)

미시험으로 남은 단 하나는 **실 SDR OTA 경로**다. ZMQ 공유의 도착률 상한(~61/s)과
CU 부하-지터 결합이 그 경로에서 달라질 수 있으나, 본 세션에서 확인하지 못했다.

## 거절-천장 결합 확정 (n=1,789)

앞서 이 결합은 2 UE 런의 **거절 5건**으로 세운 결론이었다. 중재 런에서 1,789건으로 재검증:

| 거절 시점 점유 | 비율 |
|---|---|
| **96 (천장)** | **97.8%** |
| ≥ 94 | 98.0% |
| < 91 | 1.9% (런 양 끝단 과도 구간) |

**우회로 없음.** 거절을 얻으려면 점유가 천장에 있어야 한다.

## 점유의 시간 분포 — 천장이 자연 위치보다 3.5 위에 있다

| 점유 | 시간 비율 |
|---|---|
| 96 | 27.0% |
| 95 | 10.6% |
| 94 | 20.7% |
| 93 | 12.6% |
| 92 | 7.9% |
| 91 | 6.7% |

평균 **92.5**, 94~96 구간에 **58.3%**. 천장 96은 시스템이 머무는 자리보다 3.5 위다.
(천장이 94였다면 체류가 58.3%로 올라 공백이 붕괴했을 것이다.)

필요: 평균 점유 +3.5 → 수락 +2.4/s 또는 T_slot +62 ms. **둘 다 막혔다.**

## 목표를 충족시키는 단일 변경 (gNB 측, 팀 결정 사항)

평형 용량 = `수락률 × T_slot = 42.5 × 2.197 =` **93.4 컨텍스트**.
점유가 천장 `C`를 상시 누르려면 `93.4 ≥ C`가 필요하고 현재 `C = 96`이다 — **3 초과.**

점유 시간 분포에서 역산한 천장별 체류율:

| 천장 C | 체류율 (= P(점유 ≥ C)) |
|---|---|
| 96 (현재) | 27.0% |
| 94 | 58.3% |
| 93 | 70.9% |
| 92 | 78.8% |
| 91 | 85.5% |
| **90** | **90% 이상** |

`C = 90`에서: 점유 상시 밀착, 수락 `90/2.197 = 41.0/s`,
거절 `61.3 − 41.0 =` **20/s** → 균등 간격 **50 ms** → **목표 충족.**
(C=90에서 수락 41.0/s는 현재 실측 42.5/s 이내이므로 자기일관적이다.)

**즉 필요한 것은 DU 선언 용량을 96 → 90 으로 내리는 것 하나다** (SR/CSI 자원 설정).
모드 B에서 SR 자원이 12로 용량을 정하고 실측 피크 점유가 정확히 12였으므로,
이 설정이 천장을 정한다는 것은 이미 실측으로 확인됐다.

**단 이것은 gNB 설정 변경이며 "기지국 무수정" 제약 대상이다.**
도구 측에서 할 수 있는 일이 아니고, 팀 공용 테스트베드의 변경이므로 사용자/팀 결정 사항이다.
변경하면 "상용 블랙박스 CU 전제"라는 프로젝트 전제와의 관계도 다시 따져야 한다 —
천장을 우리가 고를 수 있다면 그 실험은 더 이상 주어진 셀에 대한 공격이 아니다.
